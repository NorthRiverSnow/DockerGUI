## 命名

**名前と型だけで、何を返すか・何を受け取るかが分かるようにする。**
コメントの規則 1（名前と型で言えるか）はこれが前提。

### 決まっている形

<!-- プロジェクトで実際に使っている形を並べる。下は例 -->

| 形                | 使うとき                             | 例                          |
| ----------------- | ------------------------------------ | --------------------------- |
| `〜Of(source, …)` | source から引く・導く                | `userOf` `pathOf`           |
| `is〜`            | 真偽を返す                           | `isDone` `isEmpty`          |
| `read〜(stored)`  | 保存された、形が保証されない値を読む | `readConfig` `readSaved`    |
| `SCREAMING_SNAKE` | モジュールの定数                     | `RETRY_LIMIT` `DEFAULT_DIR` |

### 関数は 動詞 + 目的語

**呼ぶと何が起きるかが、名前だけで分かる形にする。**
`✗ userData()` `✗ process()` → `○ loadUser()` `○ validateInput()`

動詞が要らないのは、**何を返すかが形で分かるとき**だけ（`userOf(list, id)`、`isDone(state)`）。

**引き方が複数あるなら、条件を名前に出す。**
`✗ findUser(id)` と `findUserByEmail(email)` → `○ findUserById(id)` と `findUserByEmail(email)`。
**2 つ目の引き方が出たときに、両方に足す**——片方だけ付けると、どちらが既定か読めなくなる。

### 付ける前に、上から確かめる

1. **返すものを名乗っているか。** 呼ぶ先の都合で名付けない
   `✗ dataForView` → `○ visibleRows`
2. **目的語がずれていないか**
   `✗ dropUsers`（利用者を消す？） → `○ resetUserStats`（利用者の**記録**を消す）
3. **同種の関数と動詞が揃っているか**
   `✗ dropCache` と `resetIndex` → `○ resetCache` と `resetIndex`
4. **対になる関数と区別が付くか。** 単位や範囲が違うなら名前に出す
   `✗ count` と `total` → `○ answeredQuestions` と `answerCount`
5. **仕様書の言葉を使っているか。** 比喩と内部語を避ける
   `✗ pool` → `○ targetItems`（仕様の「処理の対象」）
6. **引数の名前が、何が入るかを言っているか**
   `✗ parsed`（何をパースした？） → `○ stored`（保存から読んだ、形が保証されない値）
7. **引数の順が同族と揃っているか**
   `✗ f(items, source)` と `g(source, item)` → `○ どちらも (source, …)`
8. **判断に名前が付いているか。** 条件式を裸で置かない
   `✗ all.every((x) => selected.includes(x))` → `○ isEverySelected(all, selected)`

### 短縮しない

`of` `res` `val` `tmp` のような名前を使わない。**テストのヘルパも同じ**で、
何を固定したかを名前に入れる（`✗ of(a, b)` → `○ emptyProgress(counts, answers)`）。

### 置き場所も名前の一部

**共通部分は、使う側の都合ではなく中身で分ける。**
**同じ処理が 2 箇所に出たら、3 箇所目を書く前に共通へ移す。**

## コメント

**書く前に、上から順に判断する。** 途中で「書かない」に当たったら、そこで終わり。

1. **名前と型で言えるか** → 言えるなら書かない
2. **docs に書いてあるか**（仕様・設計の判断）→ 書いてあるならコードには書かない。
   場所を示す必要があるときだけ**参照だけ**を書く。文を写さない
3. **他のファイルに同じ文を書いていないか** → 2 箇所に要るなら、それは docs か Skill の規則。
   1 本化して、コードからは消す
4. ここまでで消えなかったものだけ、次の 3 つの形で書く

| 形       | 中身                                                                   |
| -------- | ---------------------------------------------------------------------- |
| `/** */` | 呼ぶ側が知る必要のある振る舞い（短絡する / throw する / 副作用がある） |
| `why:`   | 言語・OS・ライブラリの挙動から来る理由（そう書かないと壊れる理由）     |
| `TODO:`  | 暫定の配置。**動かす先と時期**を書く                                   |

**意図的な不在は `why:` で書く。** 無いものはコードに現れないので、これでしか残せない。

**引数と戻り値の説明は、呼ぶ側に出る形で書く。** ブロックコメントはエディタが拾わない。

**`@returns` は書かない**——型と関数名で分かる。

**経緯は書かない。** 「以前は X だったが Y にした」は git log の役目。

### why の書き方

**「何が起きるか → どうしたいか」で書く。** 状況の説明だけでは、読む人が判断に使えない。

```
✗  実データに 3 本ある
○  連続する改行をまとめると行が 1 つ減り、間を空けて区切っていた文が地続きに見える
```

**調査した時点の数値は書かない。** 「153 行中 4 本」は元データが変われば嘘になる。
残すのは、いつでも成り立つ因果のほう。

**当然の疑問に先回りする。** 「中身が空なら 0 では？」に答えていないと、
その処理が成立している理由が読めない。

## 日本語の書き方

**コメント・テスト名・docs・チャットのすべてに適用する。** 詳しくは Skill の `writing-ja`。

### 主語と目的語を省略しない

```
✗ 外した項目は、開き直しても外れている
○ 一覧の項目のチェックを外すと、画面を開き直してもその項目のチェックは外れたまま
```

### 多義語を使わない

```
✗ lint で落とす        ○ lint エラーにする
✗ テストが落ちる        ○ テストが失敗する
✗ サーバを上げる        ○ サーバを起動する
✗ ルールが効く          ○ ルールが適用される
```

## 進め方

**1 ステップ = 1 レビュー。各ステップの終わりで止まる。**

一度に大量のファイルを出すとレビューできない。原則 **1 ステップ 1〜3 ファイル**、
変更点が一目で追える量に留める。次のステップに勝手に進まない。

前のステップで固めたものを後のステップで黙って変えない。変える必要が出たら、
それは前のステップの設計ミスとして報告する。

詳しくは Skill の `step-plan`。

## テスト

## 結論する前に確認する

- `which` が空でも「未インストール」と結論しない。**絶対パスで確認する**
- **リポジトリを見れば分かることを質問しない**
- 成果物のドキュメントに、頼まれていない用語訂正や注意書きを混ぜない
- **エラーメッセージを推測しない。** 実際に動かして出力を読む

---

## 環境を壊さない

- **利用者が起動したプロセスを止めない。** 検証用のサーバは別ポートで立て、
  終わったら**自分が起動したものだけ**を PID 指定で止める
- ポート名やプロセス名での一括 kill をしない
- 生成物（`dist/` など）を作ったら片付ける
