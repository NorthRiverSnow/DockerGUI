# 設計方針

**何をどう作るかを決める前に、何を守るかを決める。** 設計方針に反する設計は採らない。

## 前提になる制約

設計を左右する制約が 2 つある。どちらも技術で解決できないので、設計で受け止める。

### 1. 開発者は Windows の WSL 環境を持っていない

**Windows 側の動作を実機で確認できない。** 書いたコードが Windows で動くかどうかを、
出荷前に自分で確かめられない。

Windows で確認できないことに対して、次の 3 つで備える。

- **Windows でしか確認できないコードの量を、設計で減らす。**
  同じ通信の仕組みを macOS でも使えるようにして、macOS で毎日動かす（原則 4）。
- **残った部分を純関数に閉じ込め、入力と出力を単体テストで固定する。**
  `wsl.exe` に渡す引数の組み立て、接続先の判定、パスの変換の 3 つ（原則 3）。
- **診断の画面をアプリに組み込み、利用者から状況を受け取る。**
  Windows で使う人が貼り付けた診断の結果が、開発者にとって唯一の実地の情報になる（原則 10）。

### 2. 開発者にデスクトップアプリの開発経験が無い

**詰まったときに調べて答えが見つかる技術を選ぶ。** 利用者が少ない技術は、
不具合に当たったときに前例が見つからず、そこで作業が止まる。

## 技術選定

| 層 | 選ぶもの | 理由 |
| --- | --- | --- |
| 土台 | Electron | エンジンへの接続は「unix ソケット」「名前付きパイプ」「子プロセスの標準入出力」という OS 依存の低い層の操作で、Node の標準ライブラリだけで全部書ける |
| 言語 | TypeScript | main・preload・renderer・テストを 1 つの言語で書ける。型検査を各ステップの終了条件にできる |
| ツールチェーン | Vite+（`vp`） | パッケージ管理・テスト・lint・整形・タスク実行を 1 つのコマンドで行える |
| 画面 | React | 資料が最も多く、詰まったときに調べがつく |
| 画面の部品 | Mantine 9（9.6.2 で確認） | 下に理由を書く |
| 国旗 | `circle-flags` 2.8.3 | 丸い国旗の SVG 集。使う旗だけをアプリに同梱でき、外部のサーバから読み込まない |
| アイコン | Phosphor Icons（`@phosphor-icons/react` 2.1.10 で確認） | Mantine 9 の文書が勧めている。Mantine の文書の例で使われ、Mantine のパッケージにも依存するものがある（Mantine の文書で確認） |
| 見た目 | CSS Modules（Vite に同梱） | 部品ごとに CSS のファイルを分けられ、クラス名がほかの部品とぶつからない。Mantine の見た目もふつうの CSS なので、見た目の付け方が 1 つで済む |
| CSS の検査 | stylelint 17 と `stylelint-use-logical` 2（17.15.0 と 2.1.3 で確認） | 原則 15 と原則 16 を検査で守らせる。Vite+ に同梱されていないので、別に入れる |
| Electron のビルド | electron-vite 5（安定版）+ Vite 7 | main・preload・renderer の 3 つを 1 つの設定でビルドでき、preload を CommonJS で出力する設定を持つ |
| テスト | Vitest 4（Vite+ 0.3.3 に同梱の 4.1.11） | 別途の導入が要らない |
| 画面のテスト | jsdom 30 と Testing Library（`@testing-library/react` 16.3.3 で確認） | Electron を起動せずに、Vitest の中で View を描き、ボタンを押せる。Testing Library は、画面を読む人と同じく、ボタンの名前で要素を探す |
| lint と整形 | oxlint と oxfmt（Vite+ に同梱） | ESLint と Prettier を別途入れずに済む |
| 画面部品の確認 | Storybook 10（10.6.0 で確認） | Electron を起動せずに、コンテナが 1 つも無いときや失敗したときの見た目を確認できる |
| ログの記録 | `electron-log` | OS ごとの置き場所の判定、ファイルの回転、renderer からの転送を自分で書かずに済む |
| ターミナルの表示 | `@xterm/xterm` | ターミナルの制御文字を解釈して画面に出す部分を自分で書かずに済む |
| 値の検査 | zod 4（4.6.5 で確認） | スキーマから TypeScript の型を作れるので、検査と型を 2 回書かずに済む。資料が多い（原則 12） |
| エンジンとの通信 | Engine API を叩く自作の薄い層 | 下に理由を書く |
| Compose | `docker compose` を子プロセスとして実行する | Compose は Engine API に無く、CLI のプラグインとして提供されている。子プロセスとして実行する以外に道がない |

### Electron を選び、Tauri を選ばない理由

Tauri は配布するファイルが小さく、使うメモリも少ない。それでも Tauri を選ばない理由が 2 つある。

- **Tauri はバックエンドを Rust で書く。** エンジンへの接続は Rust で書くバックエンドの仕事で、
  開発者に Rust の経験が無く、開発機にも入っていない。
- **Tauri は OS ごとに描画エンジンが分かれる**（macOS は WebKit、Windows は WebView2）。
  **Windows 側を実機で確認できない**以上、macOS で見た通りに Windows でも表示される保証が要る。
  Electron は両方の OS で Chromium を同梱するので、描画エンジンの差が出ない。

配布するファイルの大きさとメモリの使用量は、開発者本人の開発機で動かすだけなので問題にならない。

### エンジンとの通信を自作し、dockerode を使わない理由

- **使う Engine API は多いが、ほとんどは URL を組み立てて JSON を読むだけ。**
  一覧は `design/main.md` に置く。手間がかかるのはストリームの読み取りの 4 つで、
  そのうち形が特殊なのは、ログの枠とターミナルの接続の乗っ取りの 2 つ（`design/main.md` の「ストリームの読み方」）。
- **dockerode は、DockerGUI が使わない機能のための依存を連れてくる。**
  dockerode 5.0.1 は、ビルドのための gRPC（`@grpc/grpc-js`）・`protobufjs`・`tar-fs` を、
  下で使う docker-modem 5.0.7 は SSH の実装（`ssh2`）を連れてくる（npm の登録情報で確認）。
- **dockerode 本体と型定義でメジャー版が食い違っている**（本体 5.0.1、`@types/dockerode` 4.0.1）。
  型検査を各ステップの終了条件にする進め方と噛み合わず、型の不一致を自分で埋める作業が発生する。
- **画面に出す形に直結した型を、最初から定義できる。** 既存のライブラリの型を
  画面用の型へ直す層が 1 つ減る。

**接続の乗っ取りを、自作で作れることを確かめた**（`design/main.md` の「使う Engine API の一覧」の「ターミナル」）。

### 画面の部品に Mantine を使う理由

**仕様で決めた振る舞いの多くを、自分で作らずに済む。**

| 仕様で決めた振る舞い | 自分で作るときに要ること |
| --- | --- |
| 確認の画面（`spec/common.md` の「取り返しのつかない操作は、確認を挟む」） | 画面の後ろを押せなくする。キーボードの操作が確認の画面の外に移らないようにする。`Esc` で閉じる |
| メニュー（配色と言語の選択、一覧の行のメニュー） | 矢印キーで項目を移る。メニューの外を押したら閉じる。画面の端で位置をずらす |
| タブ、スケルトン、通知、コピーのボタン | 部品ごとの振る舞いと見た目 |
| 配色（`spec/common.md` の「配色」） | すべての部品について、ライトとダークの 2 通りの色を決める |

**why: 表の右の列は、動かして初めておかしいと気づく処理。** 自分で作ると、表示が崩れる箇所がその分だけ増える。
ライブラリの部品は、多くの利用者が使って直してきたものを使える。

| 候補 | 採らない理由 |
| --- | --- |
| 部品のライブラリを使わない | 表の右の列を、全部自分で作ることになる |
| MUI | 見た目の付け方が Emotion（JavaScript の中に CSS を書く仕組み）で、自分で書く CSS Modules と 2 つの仕組みが混ざる。崩れたときに、どちらの仕組みで崩れたかを調べることになる |
| shadcn/ui | Tailwind CSS と、パスの別名（`@/`）が要る。パスの別名は使わないと決めてある（`design/directories.md` の「共有する型は `src/shared` に置く」）。部品のソースコードがリポジトリに入り、部品の保守も自分ですることになる |

**Mantine を使う代償を先に書く。**

- **PostCSS（CSS を変換する道具）の設定が要る**（Mantine の Vite の手引きで確認）。`postcss` `postcss-preset-mantine` `postcss-simple-vars` を入れ、`postcss.config.cjs` を置く
- **大きな版の更新は、ここ数年は年に 1 回ほど出ている**（8.0.0 が 2025 年 5 月、9.0.0 が 2026 年 3 月）。版はロックファイルで固定されるので、`vp update` を実行しない限り変わらない。大きな版に上げるときは、Storybook で状態ごとの見本を開いて、崩れた箇所を確かめる

### Vite が 2 つ入る理由と、2 つの Vite の役割の分担

Vite+ は Vite 8 を同梱している。一方、electron-vite の安定版が受け付ける Vite は 7 までで、
Vite 8 に対応した electron-vite 6 は beta しか出ていない。
**制約 2（前例が見つかる技術を選ぶ）に従い、beta を使わず安定版を取る。**

安定版を取るため、プロジェクトの依存に Vite 7 を入れる。**衝突しないのは、2 つの Vite が使われる場面が
分かれているため。**

| Vite の出どころ | 版 | 使う場面 |
| --- | --- | --- |
| Vite+ に同梱 | 8 | `vp test` と `vp build` が内部で使う（Vite+ 0.3.3 で確認。`vp test` の Vitest は、Vite+ に同梱の Vite 8 を読み込む） |
| プロジェクトの依存 | 7 | `electron-vite` が main・preload・renderer をビルドするときに使う |

**アプリのビルドに `vp build` は使わない。** `vp run build` が `electron-vite build` を呼ぶ形にする。

**プロジェクトの中の Vite を、Vite+ の Vite に置き換える設定（pnpm の `overrides`）を入れない。**
`vp create` の雛形はこの設定を入れる。入れると、electron-vite にも Vite 8 が渡る。electron-vite 5 が受け付ける Vite は 7 まで（npm の登録情報の `peerDependencies` で確認）。

### Storybook を使う条件

Storybook は Electron ではなく**ブラウザ**で画面部品を描く。`window.api`（preload が渡す橋）が
存在しないため、次の 2 つを守らないと描けない。

- **View は `window.api` を直接呼ばない**（原則 14）。
- **main を呼ぶ処理を `src/renderer/src/api` に集める**（`renderer.md` の「main の窓口」）。Storybook では main の窓口を差し替える。

**Storybook はテストではなく、見た目を確認する手段として使う。** 動きは、画面のテスト（`renderer.md` の「View のテスト」）で確かめる。
「振る舞いには書く。見た目には書かない」（`CLAUDE.md` の「テスト」）は変えない。
Storybook が担うのは、Electron を起動せずに、コンテナが 1 つも無いときや
接続に失敗したときの見た目を確かめることに限る。

導入するのは**最初の画面を作り始める段階**。表示するものが無いうちに入れても、空の画面を見るだけになる。

## 開発で使うコマンド

**コマンドは `vp` に統一する。** `npm` `pnpm` `npx` `vitest` `eslint` `prettier` を直接実行しない。

| 行うこと | コマンド |
| --- | --- |
| 依存の導入 | `vp install` |
| 依存の追加 | `vp add <パッケージ名>` |
| 開発用の起動 | `vp run dev` |
| 見た目の確認（Storybook） | `vp run storybook`。`http://localhost:6006` を開く |
| ビルド | `vp run build` |
| テストの実行 | `vp test` |
| 整形・lint・型検査をまとめて実行 | `vp check` |
| 整形と lint の自動修正 | `vp check --fix` |
| CSS の検査（原則 15、原則 16） | `vp run lint:css` |

**各ステップの終了条件は、`vp check` と `vp test` と `vp run lint:css` が、すべて正常終了すること。**
`vp run lint:css` は、stylelint を呼ぶタスク。stylelint は Vite+ に同梱されていないので、`vp check` に含まれない。

**`vp run dev` は、main と preload のファイルを変えると、作り直してアプリを起動し直す**（`package.json` の `dev` で `electron-vite dev --watch` を実行する）。
renderer のファイルを変えたときは、アプリを起動し直さずに画面だけが新しくなる。

**why: `--watch` を付けないと、main と preload は、アプリを起動し直すまで古いままになる。**
画面だけが新しくなり、新しいボタンを押しても、古い preload が知らない口の呼び出しを断るので、何も起きない。

**`vp install` の後に、`postinstall` が Electron の本体を入れる**（`package.json` の `postinstall` で `install-electron` を実行する）。
Electron 44 は、パッケージを入れたときには本体をダウンロードしない。
pnpm が依存を入れ直して Electron のパッケージの置き場所が変わると、新しい置き場所に本体が無い状態になり、`vp run dev` が起動できない（開発機で確認）。

## 守る原則 — 構成と安全

### 1. エンジンへの接続は main が独占する

renderer に Node の機能を渡さない。`contextIsolation` を有効、`nodeIntegration` を無効、
`sandbox` を有効にする。

**why: renderer は画面を描く場所で、コンテナを削除できる権限を持つ場所ではない。**
将来ログの内容や外部のライブラリを画面に表示するようになったときに、
表示した内容がそのまま Docker の操作に繋がる経路を作らない。

**`sandbox` を有効にする代償を先に書く。** `sandbox` を有効にした preload は ESM の `import` を使えないため、
preload は CommonJS で出力する。ビルドの設定に最初から入れる。

### 2. renderer は Docker の語彙を扱わない

画面に出すためのデータ型を Engine API の応答とは別に定義し、変換は main 側の純関数に集める。

**why: Engine API の応答の形は、エンジンの版によって変わる。** 変換を画面側に散らすと、
版が変わったときに直す場所が画面全体に散らばる。

### 3. Windows でしか確認できないコードを、少数の純関数に閉じ込める

次の 3 つに限定し、いずれも入力と出力を単体テストで固定する。

- `wsl.exe` を前に付けた、子プロセスの引数の組み立て
- コンテキストの一覧から接続先を判定する処理
- Windows のパスを WSL のパスに変換する処理

**why: 実機で確かめられないものは、テストで固定するしかない。**
閉じ込める先を純関数にすれば、OS に関係なく開発機でテストを実行できる。

### 4. 同じ通信経路を macOS でも選べるようにする

接続方式を設定の画面から手で選べるようにし、Windows の WSL 向けに作った
「子プロセスを通信路にする」経路を、macOS でも選べる状態にする。

**why: `docker system dial-stdio` は macOS の Docker でも動く。**
同じ経路を開発機で日常的に動かせば、子プロセスの後始末・HTTP の接続の使い回し・
ストリームの分離といった処理の誤りが、Windows に届く前に開発機で表面化する。

### 5. 定期的な取得をしない

一覧の更新は Engine API の `/events` の購読で行う。一定の間隔で一覧を取り直すことはしない。

**why: 間隔を短くするとエンジンへの要求が増え続け、長くすると画面の表示が実際の状態から遅れる。**
`/events` はコンテナの状態が変わった瞬間に通知を送るので、どちらも起きない。

**例外は、接続していないエンジンが起動したかどうかを確かめる場合。**
`/events` は接続しているエンジンからしか届かないので、
接続していないエンジンの起動を知らせる仕組みが存在しない。
確かめに行く以外の方法が無いため、定期的に確かめる（`spec/connection.md`）。

### 6. Engine API の版を URL に必ず書く

起動時に `/version` を呼んで、エンジンが対応する版とアプリが対応する版の小さいほうを選び、
以降のすべての要求で `/v1.xx/` を前に付ける。

**why: 版を書かずに要求すると、エンジンは動いている環境で最も新しい版として応答する。**
利用者ごとにエンジンの版が違うため、応答の形が環境ごとに変わり、開発機では出ない不具合が起きる。

### 7. IPC に背圧を入れる

main から renderer へストリームを送るときは、一定の時間ぶんをまとめて 1 回で送る。
renderer から受信の確認を返し、確認されていない送信が上限に達したら main は送信を止める。
止めている間に溜まった行は捨て、省略したことが分かる行を画面に差し込む。

**why: ログが毎秒数千行出るコンテナがある。** IPC は送りっぱなしで、
renderer が処理し切れなくても送信は止まらない。背圧を入れないと画面が操作を受け付けなくなる。

**省略した区間は、捨てた行の時刻の範囲を差し込んだ行に持たせ、利用者の操作で取り直せるようにする。**
コンテナのログの原本は Docker のエンジンに残っているので、`since` と `until` を指定すれば
同じ区間をあとから取得できる。**捨てるのは画面への表示だけで、読めなくなるわけではない。**

**why: 差し込んだ行に「何行省略した」としか書かないと、読む人はそこで行き止まりになる。**
時刻の範囲を持たせておけば、省略した区間だけを取り直して読める。
ただしコンテナのログドライバが `none` の場合と、Docker 側の回転で古い部分が消えた場合は
取り直せない。**取り直せなかったことを画面に出す。**

### 8. 開いたストリームの後始末を、main の登録簿が持つ

開いたストリームに識別子を振って main 側の登録簿に記録し、画面を閉じたときと
ウィンドウが破棄されたときに、登録簿を通じてまとめて閉じる。

**why: ストリーム 1 本につき子プロセスが 1 つ起動する構成になる。**
閉じ忘れると `wsl.exe` の子プロセスが残り続け、ログの画面を開くたびに増えていく。

### 9. 失敗は IPC の境界で値に変換する

main 側で発生した失敗は、IPC を越える前に「何に失敗したか」を表す値に直す。
renderer には例外を投げない。

**why: 例外は IPC を越えると構造を失う。** `Error` に付けた独自の属性が消え、
renderer 側には文字列しか届かず、画面で失敗の種類ごとに表示を分けられなくなる。

#### 想定した失敗と、想定していない失敗

**失敗を 2 種類に分け、種類ごとに流れを 1 つに決める。**

| 種類 | 何が当たるか | main がすること | 画面に出すもの |
| --- | --- | --- | --- |
| 想定した失敗 | エンジンが失敗の応答を返した（削除を断った、イメージが見つからない）。エンジンに接続できない。子プロセスが 0 以外の終了コードで終わった | 失敗の種類と、画面の文に要る情報（対象の名前、エンジンが返した文）を値にして返す | 種類ごとに決めた文（`spec/common.md` の「失敗の見せ方」） |
| 想定していない失敗 | 想定した失敗に当たらないものすべて。DockerGUI の不具合で起きた例外、読めない形の応答 | IPC の境界で例外を受け止め、スタックトレースと一緒にログに書く。画面には「想定していない失敗」という種類だけを返す | 共通の文と ［ログのフォルダを開く］（`spec/common.md` の「想定していない失敗」） |

**どちらに当たるかは、DockerGUI が失敗の起き方を知っているかどうかで決める。**
エンジンが返した失敗の応答は、言い換えの表に無い文でも、想定した失敗として扱う
（`spec/images.md` の「取得の失敗」——言い換えられない文は、エンジンが返した文をそのまま出す）。

**renderer で起きた例外も、想定していない失敗として扱う。** main に送ってログに書き（原則 11）、
画面には同じ共通の文を出す。

**why: 想定していない失敗の原因は、画面に出さない。**
スタックトレースは開発者が読むもので、利用者が読んでも次にすることを決められない。
ログに残し、利用者からログを受け取って開発者が読む（原則 11）。

### 10. 診断の機能をアプリに組み込む

接続に失敗したときに、次のものを画面に表示する。**そのままコピーして貼り付けられる形**にする。

- 試した接続方式と、試した順序
- 実際に起動した子プロセスの引数
- 子プロセスが標準エラー出力に書いた内容
- `wsl.exe -l -q` で得たディストロの一覧と、各ディストロでの `docker version` の結果
- エンジンへの疎通（`GET /_ping`）の結果

**why: 開発者は Windows の環境を持っておらず、手元で再現できない。**
利用者が貼り付けた診断の結果が、原因を切り分ける唯一の材料になる。

### 11. ログをファイルに残し、利用者から受け取れる形にする

main がログファイルを 1 本持つ。renderer で起きた失敗も main に送り、同じファイルに書く。
ファイルは一定の大きさで回転させ、際限なく増やさない。

| 記録する | 記録しない |
| --- | --- |
| 接続の確立と切断。使った接続方式 | 一覧の取得のような、読むだけの要求（失敗したときだけ記録する） |
| 子プロセスの起動と終了。起動では引数、終了では終了コード | コンテナのログの中身 |
| 子プロセスが標準エラー出力に書いた内容 | レジストリの資格情報と、環境変数の中身 |
| 状態を変える操作（起動・停止・削除・取得など）の開始と終了。終了では、結果とかかった時間 | |
| ストリームの開始・省略・終了 | |
| 想定した失敗の種類と原因。想定していない失敗のスタックトレース（原則 9） | |

**ストリームには短い連番の識別子を振る**（`logs-1` `exec-1` `events-1`）。UUID は使わない。

**why: 開発者は Windows の環境を持っていないので、利用者が貼り付けたログが、経過を知る唯一の材料になる。**
ログを人が目で追うため、識別子を連番にする——UUID が並ぶと、
同じ識別子かどうかを目で確かめられない。
読むだけの要求とコンテナのログの中身を記録しないのは、量が多く、他の行が埋もれるため。

**why: 状態を変える操作は、開始と終了の両方を記録する。**
終わらない操作は、開始の行があって終了の行が無いことで見つかる。
`colima start` が止まったときのように、利用者が「反応が無い」としか伝えられない場面で、
どの操作で止まったかをログから読める。
開始と終了の行は、操作の名前と対象の名前で対応づける。**操作ごとの識別子は振らない**——
利用者は 1 人で、同じ対象への同じ操作は重ならない（`spec/common.md` の「実行中は、同じ操作を受け付けない」）。
資格情報を書かないのは、利用者がログをそのまま貼り付けるため。

**ログの文は英語で書き、画面の言語によって変えない**（`spec/common.md` の「画面の言語」）。

**why: 画面の言語に合わせると、言語を切り替えた前後で、1 本のファイルに 2 つの言語が混ざる。**
英語に固定すると、Docker が返す英語の文や、失敗の `code` と同じ言語で並ぶ。
英語で使う利用者から受け取ったログも、同じ形で読める。

### 12. 外から来る値は、入ってくる境目で検査する

**形が保証されない値は、DockerGUI に入ってくる境目で 1 回だけ zod のスキーマで検査する。**
検査を通った値だけを、内側の層に渡す。

| 値 | 検査する場所 | 検査に失敗したら |
| --- | --- | --- |
| Engine API の応答 | Engine API 層（`design/main.md`） | 想定していない失敗（原則 9） |
| 設定ファイル | 機能層の設定 | `spec/settings.md` の「設定ファイルを読めないとき」 |
| 子プロセスが出力する JSON（`docker compose ls` など）と `~/.docker/config.json` | 読み込む機能層のモジュール | 想定していない失敗 |
| renderer から IPC で届く値 | IPC 層（`design/ipc.md`） | 想定していない失敗 |

**Engine API の応答は、DockerGUI が使う項目だけを検査する。** 使わない項目は検査せずに通す。

**why: TypeScript の型は、ビルドのときにしか働かない。** 動いているときに届いた値が型のとおりかどうかは、
検査しないと分からない。型のとおりでない値が内側まで届くと、画面に値の無い欄が出たり、
届いた場所から離れたところで例外が起きたりして、原因を追えなくなる。

**why: 使う項目だけを検査する。** 全部の項目を検査すると、エンジンの版が上がって項目が増えたときや、
使っていない項目の形が変わったときにも失敗になる。利用者ごとにエンジンの版が違う（原則 6）。

**why: renderer から届く値も検査する。** renderer は、コンテナのログのような外の内容を画面に出す場所で、
main は renderer から届いた値を信用しない（原則 1）。

**zod は TypeScript 5.5 以降と、型検査の `strict` の設定を求める**（zod の文書で確認）。
Vite+ の型検査が使う TypeScript の版は確かめていないので、zod を入れるときに確かめる。

## 守る原則 — コードの書き方

### 13. 関数で書く。クラスは必要なときだけ使う

既定は、純関数とクロージャで書く。状態は判別可能なユニオン型で表し、失敗は値として返す。

**クラスを使ってよいのは、Node の API がプロトタイプの継承を要求する次の 2 つだけ。**

| 使う場所 | 継承するもの | 継承が要る理由 |
| --- | --- | --- |
| 子プロセスの標準入出力を通信路にする被せもの | `stream.Duplex` | Node の HTTP クライアントが、渡された通信路を `net.Socket` として扱うため |
| HTTP の接続の作り方を差し替えるもの | `http.Agent` | Node の HTTP クライアントが `Agent` の `createConnection` を呼ぶため |

**why: DockerGUI の処理の大半は「受け取った値を別の形に直す」ことで、状態を抱える必要がない。**
純関数にすれば、OS にも Electron にも依存せずにテストを実行できる。
逆に表の 2 つは、Node が「継承したクラス」を前提に動くため、関数では置き換えられない。

### 14. renderer を Model・View・Controller に分ける

| 役 | 持つもの | 持たないもの |
| --- | --- | --- |
| Model | 画面に出すデータの型と、データの状態。状態を次の状態へ進める純関数 | main を呼ぶ処理。DOM を触る処理 |
| View | props を受け取って要素を返す関数コンポーネント | 自分の状態。main を呼ぶ処理 |
| Controller | 利用者の操作を受けて main を呼び、返ってきた結果を Model に渡す処理。React の hook として書く | 要素を返す処理 |

**why: View が main を呼ばないので、Storybook が View をそのまま描ける。**
加えて、テストの対象が Model と Controller に寄る。
「壊れても動かしただけでは気づけないもの」（`CLAUDE.md`）は状態の遷移とイベントの結線であって、
要素の見た目ではない。View に判断を置かなければ、見た目のテストを書かずに済む。

### 15. CSS の余白と位置は、左右ではなく、行の始まりと終わりで指定する

| 使わない | 使う |
| --- | --- |
| `margin-left` `margin-right` | `margin-inline-start` `margin-inline-end` |
| `padding-left` `padding-right` | `padding-inline-start` `padding-inline-end` |
| `border-left` `border-right` | `border-inline-start` `border-inline-end` |
| `left` `right` | `inset-inline-start` `inset-inline-end` |
| `text-align: left` `text-align: right` | `text-align: start` `text-align: end` |

「行の始まり」は、文を書き始める側を指す。日本語と英語では左、アラビア語のように右から左に書く言語では右になる。

**why: 右から左に書く言語を追加するときに、CSS を書き直さずに済む。**
右から左に書く言語を出す予定は無い（`overview.md` の「対象にしないもの」）。
ただし、左右で書いた CSS をあとから書き換えると、全部の画面を直すことになる。最初から行の始まりと終わりで書けば、コストはほとんどかからない。

**上下の余白は、`margin-top` のままでよい。** 上から下へ行を重ねる向きは、日本語でも英語でも右から左に書く言語でも同じ。

**幅と高さも、`width` と `height` のままでよい。** 右から左に書く言語でも、幅は幅のまま。
`inline-size` のような書き方は縦書きのためのもので、原則 15 の目的には関わらない。

**CSS の中の左右の指定は、検査で見つける。** `stylelint-use-logical` が、表の「使わない」の列の指定を見つけると、`vp run lint:css` が失敗する。

**Mantine の props で余白を指定するときも、`ms` `me` `ps` `pe` を使う**（`<Group ms="md">`）。
`ml` `mr` `pl` `pr` は、左右の指定になる。
props の中の指定は、stylelint では検査できない。検査する方法は、最初の画面を実装するときに決める。

### 16. 見た目の値は、Mantine の CSS の変数で指定する

**見た目の値は、Mantine の見た目の設定（`createTheme` で作る値。`design/renderer.md` の「部品と見た目」）の 1 か所で決める。**
自分で書く CSS には値を書かず、Mantine の CSS の変数を使う。

| 値 | 書かないもの | 使うもの |
| --- | --- | --- |
| 色 | `#1a1b1e` `rgb(…)` `white` | `var(--mantine-color-text)` など |
| 余白（`margin` `padding` `gap`） | `13px` `0.8rem` | `var(--mantine-spacing-md)` など |
| 字の大きさ | `15px` | `var(--mantine-font-size-sm)` など |
| 角の丸み | `4px` | `var(--mantine-radius-sm)` など |

**why: 値を画面の CSS に書くと、その画面だけ見た目がずれる。** `theme.ts` の値を変えても、画面の CSS に書いた値は変わらない。
色は、配色を切り替えたときにその部分だけ色が変わらない（`spec/common.md` の「配色」）。
Mantine の CSS の変数は、`theme.ts` の値と配色に合わせて値が変わる。

**画面の CSS（`view.module.css`）に残るのは、どこにどう並べるかだけになる**（`design/renderer.md` の「部品と見た目」）。

**値は、検査で見つける。** stylelint の標準の検査で、`vp run lint:css` が失敗するようにする。

| 値 | stylelint の検査 |
| --- | --- |
| 色 | `color-no-hex`（16 進数の色）、`color-named`（`white` のような名前の色）、`function-disallowed-list`（`rgb()` `hsl()` などの関数） |
| 余白、字の大きさ、角の丸み | `declaration-property-unit-allowed-list`（単位を付けた値を書けないようにする） |

**ターミナルの本文の色は、`@xterm/xterm` の設定に JavaScript で渡す。** `@xterm/xterm` はコンテナの出力を自分で描くので、
CSS のファイルに書いた色を使わない。色の値は Mantine の CSS の変数から読み出して渡し、配色が変わったら渡し直す
（`design/renderer.md` の「ターミナルの本文の色は、JavaScript で渡す」）。

### 17. 流れの関数は、手順の関数を呼ぶだけにする

**いくつかの手順を順に行う関数（流れの関数）には、手順の中身を書かない。** 手順ごとに関数を作り、流れの関数はそれを呼んで、結果で分けるだけにする。

```ts
/** 接続先を探して繋ぐ。止まっていて起動する手段を知っていれば、起動してから繋ぐ。 */
async function searchAndConnect(connectionContext: ConnectionContext): Promise<void> {
  const attempt = beginAttempt(connectionContext);
  const found = await searchEngine(connectionContext);
  switch (found.kind) {
    case "running":
      await connectEngine(connectionContext, found.target, attempt, { ifUnreachable: "stopped" });
      return;
    case "startable":
      await startAndConnect(connectionContext, found.target, attempt);
      return;
    // …
  }
}
```

**`createXxx` のように値をまとめて返す関数の中に、処理を書き込まない。** 中に置くのは、持つ値の用意と、外に出す操作を関数につなぐことだけにする。
処理は外の関数にして、持つ値を引数で受け取る（例: `src/main/features/connection/connection.ts` の `createConnection` と `ConnectionContext`）。

**main の入口（`src/main/index.ts`）は、部品を作ってつなぐだけにする。** 判断や計算は、機能層か OS の窓口に置き、`index.ts` はそれを呼ぶ。
`index.ts` に書くのは、窓を作ることと、Electron の値（`app.getPath` の場所、`nativeTheme` など）を渡して機能層の部品を作ることだけ。

**口に機能層の関数をつなぐ処理は、IPC 層に、口のまとまりごとに 1 つのファイルで置く**（`src/main/ipc/connection.ts` の `registerConnectionChannels`、`src/main/ipc/app.ts` の `registerAppChannels`）。
まとまりは、`docs/design/ipc.md` の口の一覧の見出し（`connection`、`containers`、`app` …）に合わせる。`index.ts` は、作った部品を渡して呼ぶだけにする。

**why: 口は機能を作るたびに増え、全部で 50 を超える。** `index.ts` につなぐと、`index.ts` の大部分が口をつなぐ行になる。
まとまりを `ipc.md` の見出しに合わせれば、`ipc.md` の表とファイルを 1 対 1 で見比べられる。
`createXxx` ごとには分けない。配色と画面の言語は別の部品だが、どちらも `app` の口なので、`createXxx` ごとに分けると `app` の口が複数のファイルに散る。

**why: `index.ts` に処理を書くと、Electron を起動しないと確かめられない。** 機能層と OS の窓口に置けば、Electron の値の代わりを渡してテストできる。

**why: 流れと手順が混ざると、何がどの順に起きるかを、細かい処理を読み飛ばしながら探すことになる。**
流れの関数が手順の呼び出しだけなら、流れは上から読むだけで分かり、手順の中身は手順の関数を開いたときだけ読めばよい。
`createXxx` の中に処理を書き込むと、`createXxx` の中の変数に縛られて、処理を外に出せなくなる。

### 18. 書き方で意図を隠さない

| 書かない | 書く | why |
| --- | --- | --- |
| 分かれ道の条件の中に、`!` や型の書き方を詰め込む（`!(LIST as readonly string[]).includes(x)`） | 条件に名前を付けた関数にする（`if (!isNotificationChannel(channel))`） | `!` が型の書き方に埋もれると、条件を逆に読み違える |
| `as` で、型の検査をすり抜けて形を合わせる（関数に項目を後から付けて `as` で型に合わせる、など） | ふつうのオブジェクトを返す | `as` を使うと、項目の付け忘れを型の検査で見つけられない |
| 型ですでに決まっている値に、`satisfies` で型を確かめ直す | 書かない | 型で守っているように見えるが、何も増えない。実行するときに確かめているのは別の処理なのに、型で守っていると読み違える |
| 後から差し替える値を、差し替える場所を書かずに置く（最初に何もしない関数を入れておく、など） | 型の説明に、差し替える場所と差し替える値を書く（`src/main/features/connection/context.ts` の `Attempt` の `abort`） | 差し替える場所が別のファイルにあると、何もしない関数が置かれている理由が読めない |
