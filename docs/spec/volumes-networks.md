# 仕様: ボリュームとネットワーク

`common.md` の約束を前提にする。

**ボリュームとネットワークを 1 つのファイルにまとめる。**
画面の作りが同じで、DockerGUI からできることも一覧と削除の 2 つだけ。
別々のファイルにすると、同じ約束を 2 回書くことになる。

## ボリュームとネットワークに共通する約束

### できる操作

一覧の行と詳細の画面に置くボタンは、削除の 1 つだけ。

| 操作 | 押すボタン | 押せる条件 | 確認 |
| --- | --- | --- | --- |
| ボリュームの削除 | ［削除］ | すべてのボリューム | **有り** |
| ネットワークの削除 | ［削除］ | **Docker が最初から持つネットワーク以外**（「Docker が最初から持つネットワーク」を参照） | **有り** |

**使っているコンテナがあっても、［削除］ は押せる状態のままにする。**
削除を断られた時点で、使っているコンテナを並べて出す。

**why: DockerGUI が数えた件数と、エンジンが数えた件数はずれる**
（`images.md` の「使っているコンテナがあるイメージでも、［削除］ を押せる状態のままにする」と同じ）。

### DockerGUI からは作らない

ボリュームもネットワークも、DockerGUI から作る手段を置かない。

**why: ボリュームとネットワークを作るのは、コンテナと Compose。**
空のボリュームを先に作っても、使うコンテナが無ければ何も起きない。
DockerGUI で作れるようにすると、**どのコンテナからも使われないボリュームが増える**だけになる。

### 使っているコンテナは、一覧の応答に入っていない

**Engine API のボリュームの一覧にも、ネットワークの一覧にも、使っているコンテナは入っていない**
（開発機で確認）。

DockerGUI はコンテナの一覧を取り、コンテナのマウントとネットワークの設定から、
使っているコンテナを組み立てる。

### 数え方がボリュームとネットワークで違う

| 対象 | 使っているものとして数えるコンテナ |
| --- | --- |
| ボリューム | **動作中のコンテナと、停止したコンテナの両方** |
| ネットワーク | **動作中のコンテナだけ** |

いずれも開発機で確認した。停止したコンテナがつながっていたネットワークは削除でき、
停止したコンテナが使っているボリュームは削除できない。

**Docker が数え方を分けている理由は、確かめていない。**
DockerGUI は、エンジンの振る舞いに合わせて件数を数える。

## ボリューム

### 出す列

| 列 | 内容 |
| --- | --- |
| 名前 | ボリュームの名前。名前を付けずに作られたボリュームは先頭 12 文字 |
| 使っているコンテナ | 件数。0 件なら `—` |
| 大きさ | ディスクの上での大きさ（「大きさは、別に取りに行く」を参照） |
| 作成した時間 | ボリュームが作られてからの経過 |

ドライバは一覧に出さない。**ほとんどのボリュームのドライバは `local`** で、列を作っても同じ値が並ぶ。
ドライバは詳細の画面に出す。

### 大きさは、別に取りに行く

**Engine API のボリュームの一覧は、ボリュームの大きさを返さない**（開発機で確認）。
大きさを返すのは `GET /system/df`（`docker system df -v` が使うもの）で、
ボリュームの一覧とは別の呼び出しになる。

一覧の表示は、**`/system/df` の応答を待たずに出す。**

1. 名前・使っているコンテナ・作成した時間を先に出し、大きさの列には `計測中…` を出す
2. `/system/df` の応答が届いた時点で、大きさの列を置き換える

**`/system/df` にどれだけ時間がかかるかは、確かめていない。**
開発機のボリュームは中身が小さく、時間のかかる環境を再現できなかった。
**待たずに出す作りにしておけば、時間がかかる環境でも一覧が止まらない。**

### 名前を付けずに作られたボリューム

コンテナが `VOLUME` の指定で作るボリュームには、名前が付かない。
**エンジンが 64 文字の 16 進数を名前にする**（開発機で確認。
`com.docker.volume.anonymous` のラベルが付く）。

一覧では、名前の列に**先頭 12 文字**を出し、`名前無し` と添える。

```
67d4e34e733a（名前無し）        —        541.1MB        3 週間前
```

**why: 16 進数の名前は、末尾に意味が無い。**
`common.md` の「長い名前」は中央を省略する規則だが、中央を省略するのは、
イメージの名前のように末尾にタグと版が付く場合。
16 進数の名前は、コンテナ ID と同じく先頭だけを残す。

### Compose が作ったボリューム

Compose が作ったボリュームには `com.docker.compose.project` のラベルが付く（開発機で確認）。
**プロジェクトの名前は、詳細の画面に出す。**

一覧には出さない。Compose が作るボリュームの名前は `プロジェクト名_ボリューム名` の形になるので、
一覧に列を足さなくても、名前を見ればプロジェクトが読める。

### 並び順

**名前の順に並べ、名前を付けずに作られたボリュームは一番後ろにまとめる。**

**why: 名前を付けずに作られたボリュームは、名前の列に 16 進数が出る。**
16 進数を名前と混ぜて並べると、探しているボリュームの位置がずれる
（イメージの一覧でタグの無いイメージを後ろにまとめるのと同じ理由。`images.md`）。

### 絞り込み

ボリュームの名前を対象に、入力した文字を含むボリュームだけを出す。

### 1 件も無いとき

```
ボリュームが 1 件もありません
コンテナか Compose がボリュームを作ると、一覧に出ます
```

### 詳細

| 項目 | 内容 |
| --- | --- |
| 名前 | 全体を出す（`common.md` の「利用者がコピーして使いたい値」） |
| ドライバ | `local` など |
| 置き場所 | エンジンの中のパス |
| 大きさ | ディスクの上での大きさ |
| 作成した日時 | 年月日と時分秒 |
| 使っているコンテナ | コンテナの名前と状態、コンテナの中のどこにマウントされているか |
| ラベル | キーと値。Compose が作ったボリュームには、プロジェクトの名前が入る |

#### 置き場所は、利用者のパソコンのパスではない

`/var/lib/docker/volumes/…` のようなパスが返るが、**エンジンの中のパス**であって、
macOS と Windows の利用者が置き場所のパスを開いても、ファイルは見つからない。
macOS と Windows では、エンジンが仮想マシンの中で動いているため。

詳細の画面に、**エンジンの中のパスであることを添える。**

### 削除

`common.md` の「取り返しのつかない操作は、確認を挟む」に従う。

**ボリュームを削除すると、ボリュームの中のファイルが消える。**
確認の文に、中身が消えることを書く。

```
┌────────────────────────────────┐
│ ボリューム cypher-quiz_neo4j-data を削除します。               │
│ ボリュームの中のファイルも消えます。                           │
│ 元に戻せません。                                               │
│                              [ やめる ]  [ 削除する ]          │
└────────────────────────────────┘
```

名前を付けずに作られたボリュームは、**名前から中身を読めない**ことを添える。

```
┌──────────────────────────────────────┐
│ ボリューム 67d4e34e733a… を削除します。                                   │
│ 名前を付けずに作られたボリュームなので、中身が何かは名前から読めません。   │
│ ボリュームの中のファイルも消えます。元に戻せません。                       │
│                                    [ やめる ]  [ 削除する ]                │
└──────────────────────────────────────┘
```

#### 使っているコンテナがあるボリュームは、削除できない

エンジンが削除を断る（開発機で確認）。

```
remove cypher-quiz_neo4j-data: volume is in use - [1bf72c7aee3ed68c…]
```

```
┌───────────────────────────────────┐
│ ボリューム cypher-quiz_neo4j-data は、次のコンテナが使っています。   │
│                                                                      │
│   neo4j-1（正常終了）                                                │
│                                                                      │
│ 停止したコンテナも、ボリュームを使っているものとして数えます。       │
│ コンテナを削除すると、ボリュームを削除できます。                     │
│                                                  [ 閉じる ]          │
└───────────────────────────────────┘
```

**エンジンが返す文はコンテナ ID を含む。** DockerGUI はコンテナの一覧から名前を引き、名前で出す。

### まとめて削除する

一覧で複数のボリュームを選び、まとめて削除できる。
約束は `containers.md` の「まとめて操作する」と同じ。

## ネットワーク

### 出す列

| 列 | 内容 |
| --- | --- |
| 名前 | ネットワークの名前 |
| ドライバ | `bridge` `host` `null` など |
| つながっているコンテナ | 動作中のコンテナの件数。0 件なら `—` |
| 作成した時間 | ネットワークが作られてからの経過 |

**ドライバは列に出す。** ボリュームとは違い、ドライバによって働きが変わり、値もばらける
（`host` のネットワークにつないだコンテナは、エンジンのネットワークを直接使う）。

### Docker が最初から持つネットワーク

エンジンは `bridge` `host` `none` の 3 つを最初から持っていて、**削除できない**（開発機で確認）。

```
bridge is a pre-defined network and cannot be removed
```

- 一覧では、名前の列に `Docker が最初から持つネットワーク` と添える
- 3 つのネットワークの ［削除］ は、**押せない状態にする**

**why: 押せない状態にするのは、削除できないことが決まっているものだけ。**
使っているコンテナがあるボリュームとイメージは、コンテナを削除すれば削除できるようになるので、
押せる状態のままにする。`bridge` `host` `none` は、利用者が何をしても削除できない。

### 並び順

**名前の順に並べ、Docker が最初から持つネットワークは一番後ろにまとめる。**

**why: 3 つのネットワークは削除できず、利用者が操作する対象にならない。**

### 絞り込み

ネットワークの名前を対象に、入力した文字を含むネットワークだけを出す。

### 1 件も無いとき

**ネットワークの一覧が 1 件も無い状態にはならない。**
`bridge` `host` `none` は削除できないので、必ず 3 件は並ぶ。

### 詳細

| 項目 | 内容 |
| --- | --- |
| 名前 | ネットワークの名前 |
| ネットワーク ID | 全体を出す（`common.md` の「利用者がコピーして使いたい値」） |
| ドライバ | `bridge` `host` `null` など |
| 範囲 | `local` など |
| IP の割り当て | サブネットとゲートウェイ |
| 外に出られるか | エンジンの外との通信を止めているかどうか |
| 作成した日時 | 年月日と時分秒 |
| つながっているコンテナ | コンテナの名前と IP アドレス |
| ラベル | キーと値。Compose が作ったネットワークには、プロジェクトの名前が入る |

**つながっているコンテナは、ネットワークの詳細の応答に入っている**（開発機で確認。
`GET /networks/{id}` が返す）。**停止したコンテナは入らない**（開発機で確認）。

### 削除

`common.md` の「取り返しのつかない操作は、確認を挟む」に従う。

```
┌────────────────────────────────┐
│ ネットワーク cypher-quiz_default を削除します。                │
│ コンテナとコンテナの中のファイルは消えません。                 │
│ 元に戻せません。                                               │
│                              [ やめる ]  [ 削除する ]          │
└────────────────────────────────┘
```

**コンテナのデータが消えないことを、確認の文に書く。**
ボリュームの削除と並べて出ると、利用者は同じだけ危ないと考える。

#### つながっているコンテナがあるネットワークは、削除できない

エンジンが削除を断る（開発機で確認）。

```
error while removing network: network cypher-quiz_default has active endpoints (name:"web-1" id:"4053852f4cdd")
```

```
┌───────────────────────────────────┐
│ ネットワーク cypher-quiz_default は、次のコンテナが使っています。    │
│                                                                      │
│   web-1（動作中）                                                    │
│                                                                      │
│ コンテナを停止するか削除すると、ネットワークを削除できます。         │
│                                                  [ 閉じる ]          │
└───────────────────────────────────┘
```

**コンテナを停止するだけで削除できる。** ボリュームとイメージは、
コンテナを削除しないと削除できない（「数え方がボリュームとネットワークで違う」を参照）。

**エンジンが返す文はコンテナの名前を含む**（開発機で確認）。
ボリュームとイメージの断り文はコンテナ ID を返すが、ネットワークの断り文は名前を返す。

### まとめて削除する

一覧で複数のネットワークを選び、まとめて削除できる。
約束は `containers.md` の「まとめて操作する」と同じ。

**Docker が最初から持つネットワークを選んでいても、削除の対象にしない。**
`containers.md` の「選んだコンテナのうち、操作できる状態のものだけを実行の対象にする」と同じ扱い。

## 一覧の更新

ボリュームとネットワークが増減した時点で一覧を更新する。
一定の間隔で取り直すことはしない（設計方針の原則 5）。

開発機で `docker events` を見て、`volume create` `volume destroy` `network create` `network destroy`
が届くことを確認した。

**ボリュームの大きさは、イベントでは変わらない。**
コンテナがボリュームにファイルを書いてもイベントは届かないので、
**大きさを取り直すのは、ボリュームの画面を開いた時だけ。**
