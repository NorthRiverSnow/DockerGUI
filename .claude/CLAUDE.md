# DockerGUI

Docker を画面から操作するデスクトップアプリ。コンテナの起動・停止・ログ確認といった、
毎日繰り返す操作をターミナルに打ち込まずに済ませる。macOS と、Windows の WSL 環境で動かす。

## 言語

**チャットの返事・コミットメッセージ・ドキュメントは、すべて日本語で書く。**
ツールの出力、Engine API の応答、英語の文書を読んだ直後でも、返事は日本語で書く。
英語の画面の文（`messages.ts` の `en`）、エンジンが返した英語の文、公式の文書とソースコードの引用を示すときだけ、英語をそのまま引く。

## 利用者

利用者は、デスクトップアプリの開発と Docker の経験が少ない。

- 新しい用語は、使う前に 1 文で説明する
- 質問に答えた説明は、頼まれない限り docs に追加しない
- 利用者は WSL の環境を持っていない。WSL でしか確かめられないことは、確かめられないと書く

## 仕様と設計の正は `docs/`

| ファイル | 内容 |

| `docs/design-policy.md` | 設計方針。技術選定の理由、使うコマンド、守る原則 |
| `docs/design/layers.md` | 設計。層の分け方。設計の docs の一覧もここにある |
| `docs/spec/common.md` | 全画面に共通する約束 |
| `docs/spec/connection.md` | 接続と診断 |
| `docs/spec/containers.md` | コンテナ |
| `docs/spec/logs.md` | ログ |
| `docs/spec/terminal.md` | ターミナル |
| `docs/spec/images.md` | イメージ |
| `docs/spec/volumes-networks.md` | ボリュームとネットワーク |
| `docs/spec/compose.md` | Compose |
| `docs/spec/disk.md` | ディスク（使われていないデータの削除） |

- 仕様を書くときは Skill の `spec-writing` を読む
- 設計を変えるときは docs も直す。実装と docs が食い違ったら docs が正
- docs は現行仕様だけを書く。履歴（「以前は X だった」）は git log の役目

## 日本語の書き方

コメント・テスト名・docs・チャットのすべてに適用する。例と詳しい規則は Skill の `writing-ja`。

1. 主語が前の文と変わるときは、主語を書く。目的語は省略しない
2. 多義語を使わない（落とす、効く、上げる、流す）
3. **指示語と代名詞を使わない。** 名前で呼ぶ。表や節も、位置ではなく名前で呼ぶ
4. 独自の呼び方は、使う前に定義する
5. 外来語はカタカナで書く。英単語を日本語の文に混ぜない
6. 状況の説明で終わらせず、因果を書く
7. 経緯を書かない

### DockerGUI で決まっている言葉

| 使わない | 使う | 使う場面 |
| --- | --- | --- |
| この道具 | DockerGUI、アプリ | 作っているもの自体を指すとき |
| 印 | アイコン | 画面に出す絵 |
| 端末 | ターミナル、コンソール | すべて |
| 選ぶ | 選択する | 画面に表示する文 |
| 足す | 追加する | 画面に表示する文 |
| 書く | 表示する | 画面に文を表示することを説明するとき |

仕様の説明の文では「選ぶ」「足す」を使ってよい。画面に表示する文と区別する方法は、
`spec-writing` の「画面に出す文と、仕様の中の名前を分ける」。

## コードを書く

- **src を書く・直す前に、Skill の `code-style` を読む。** 名前の形、コメントを書くかどうかの判断、似た関数を 1 つにする判断、ファイルと関数の大きさ、ライブラリの中を推測しないこと、テストの書き方がある
- コマンドは `vp` に統一する。`npm` `npx` などを直接実行しない。テストは `vp test`、検査は `vp check` と `vp run lint:css`。
  一覧は `design-policy.md` の「開発で使うコマンド」
- コードの書き方の原則は `design-policy.md` の「守る原則 — コードの書き方」。名前を付けるときは Skill の `naming-review`
- **新しいライブラリや道具を入れる前に、候補を並べて利用者に選んでもらう。** 何をするか、`vp test` との相性、保守されているかを比べる表を出してから `vp add` する。
  決まっているもの: 画面の部品は Mantine、画面の振る舞いのテストは jsdom と Testing Library、見た目の確認は Storybook

## 進め方

**1 ステップ = 1 レビュー。各ステップの終わりで止まる。** 1 ステップの大きさと、ステップの終わりにすること（点検、報告の形）は Skill の `step-plan`。
次のステップに勝手に進まない。前のステップで固めたものを変える必要が出たら、黙って直さずに報告する。

**出したものは、聞く前に自分で確かめる。** 利用者に聞くのは「どちらが好みか」だけに絞る。
docs を書いたら `spec-writing` の「書いた後の点検」を当てる。
docs の枠線の図は、利用者が PlemolJP で読む前提で幅をそろえる。
`check_spec.py` には `--font ~/Library/Fonts/PlemolJP-Regular.ttf` を渡す。

## 結論する前に確認する

- `which` が空でも「未インストール」と結論しない。絶対パスで確認する
- リポジトリを見れば分かることを質問しない
- 頼まれていない用語訂正や注意書きを、成果物のドキュメントに混ぜない
- エラーメッセージを推測しない。実際に動かして出力を読む
- **Docker やライブラリの振る舞いを docs やコメントに書くときは、公式の文書（Docker の文書、Engine API の定義など）を先に確認する。**
  文書に無いことは、公式のソースコード（Docker のエンジンなら moby）で確かめ、版とファイルの場所を出典に書く。
  実際に動かした結果は、文書とソースコードを確かめる手段として使い、どちらにも無いことだけを「開発機で確認」と書く。
  報告に出典を書く形は Skill の `step-plan`

## 環境を壊さない

実際に動かして確かめる手順は Skill の `app-check`。
フック（Claude Code がコマンドを実行する前に動かすスクリプト。`.claude/hooks/guard-bash.py`）が、次の箇条書きの「イメージを取得しない」と `rm` の決まりに反するコマンドの、よくある書き方を止める。
すべての書き方を止められるわけではないので、決まりはフックに頼らずに守る。

- 利用者が起動したプロセスを止めない。自分が起動したものだけを PID 指定で止める。ポート名やプロセス名で一括 kill しない
- 利用者の `vp run dev` が動いている間は、main と preload のファイルを一時的に書き換えず、`out/` を消さない。利用者のアプリが起動し直すか、壊れる
- 生成物（`dist/` など）と一時ファイルを作ったら片付ける
- 利用者のコンテナ・イメージ・ボリュームに触らない。状態を変える確かめは、ラベル（`--label dg-list-test=1`）を付けたテスト用のものだけに行い、終わったら消す。
  利用者が許したときだけ、利用者のコンテナを操作する。操作したら、元の状態に戻す
- イメージを取得しない（`docker pull` をしない）。`docker run`・`docker create` と、`docker compose up`・`run`・`create` には `--pull never` を付ける。
  取得すると、利用者が使っている同じ名前のイメージが入れ替わる
- colima を止める前に、利用者に確認する。利用者のコンテナも一緒に止まる
- シェルは zsh。変数の値は、空白で単語に分かれない（`${=PIDS}` と書く）。`rm` の対象に変数を使わず、絶対パスで書く

## Skill とエージェント

長い作業の手順は Skill に、長い出力が出る作業はエージェント（別の文脈で動く助手）に分けてある。
**エージェントに任せると、作業の出力が会話に入らず、会話が長くなっても決まりが埋もれない。**

| 場面 | 使うもの |
| --- | --- |
| src を書く・直す | Skill の `code-style`、名前は `naming-review` |
| 仕様を書く | Skill の `spec-writing` |
| 日本語を書く・点検する | Skill の `writing-ja` |
| 作業を割る・ステップを終える | Skill の `step-plan` |
| ステップの差分を決まりで点検する | エージェントの `rules-reviewer` |
| テストを壊して確かめる | Skill の `mutation-check`。件数が多ければエージェントの `mutation-checker` |
| 実際に動かして確かめる | Skill の `app-check`。長くなればエージェントの `app-verifier` |
| 公式の文書とソースコードで振る舞いを調べる | エージェントの `source-researcher`。入れてあるライブラリの中は、Skill の `code-style` の「ライブラリの中を推測しない」 |

## git

- `main` への直 push は禁止。作業ブランチを切り、ブランチ名に何をするかを含める
- コミットと push は、指示があるまで実行しない
