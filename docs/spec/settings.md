# 仕様: 設定

`common.md` の約束を前提にする。

## 設定の画面に出すもの

**置いた画面から変えられないものだけを、設定の画面に出す。**

| 変えるもの | どこで変えるか |
| --- | --- |
| エンジンの起動の仕方、接続方式、ログの行数と保存先 | **設定の画面** |
| タグの無いイメージを出すかの切り替え（`images.md`） | イメージの画面の見出し |
| 動作中でないコンテナを隠すかの切り替え（`containers.md`） | コンテナの画面の見出し |
| ログの時刻の入切（`logs.md`） | ログの画面の見出し |
| 配色と画面の言語（`common.md` の「配色を選ぶ」「言語を選ぶ」） | 状態バーのボタンと、**設定の画面の「配色・言語」の両方** |

**why: 同じ設定が 2 箇所にあると、片方を変えたときにもう片方と食い違う。**
画面で切り替えられるものを設定の画面にも並べると、**どちらが正か読めなくなる。**

**配色と画面の言語だけは、例外として 2 箇所に置く。** 状態バーの配色のボタンは、ライトとダークを切り替えるだけで、OS の配色に合わせる状態に戻せない。
戻す場所として、設定の画面にも置く。画面の言語は、配色と一緒に探せるように、同じ分類に置く。
**どちらで変えても、もう片方の表示もすぐ変える。** 2 つは同じ保存した値を読むので、食い違わない。

**画面の切り替えは、アプリを開き直しても元のままにする。**
利用者が切り替えた状態を覚えて、次に開いたときも同じ状態にする。

**ログの追従は覚えない。** ログの画面は、開くたびに「追従中」から始まる（`logs.md` の「状態の移り変わり」）。
追従を止めるのは「いま読んでいる位置で止めたい」ときの一時的な操作で、
次にログの画面を開いたときは、最新のログを見たいことが多い。

**絞り込みの入力は覚えない。** アプリを開き直すと空にする。
絞り込みは「いま探しているもの」を入れる場所で、次に開いたときには別のものを探している。

## 画面の構成

**設定の画面を、分類の一覧と、選んだ分類の項目の 2 つに分ける。**

```
            ┌──────────┬───────────────────────────────┐
分類の一覧  │ 接続               │ エンジンの起動     (o) 自動で起動する                        │
            │ エンジン           │                    ( ) ボタンを押したら起動する              │
            │ ログ               │ 起動するエンジン   [x] colima   [x] Docker Desktop           │
            │ 設定ファイル       │ 接続するエンジン   ( ) 最後につないだエンジン                │
            │                    │                    (o) colima   ( ) Docker Desktop           │
            │                    │ 接続方式           (o) 自動  ( ) ソケット  ( ) 子プロセス    │
            └──────────┴───────────────────────────────┘
```

| 部分 | 位置 | 出すもの |
| --- | --- | --- |
| 分類の一覧 | 左 | 分類の名前。**同時に開ける分類は 1 つ** |
| 項目 | 右 | 選んだ分類の項目だけ |

**`common.md` の「画面の構成」と同じ作りにする。**
左で対象を選び、右に選ばれたものを出す形を、設定の画面の中でも繰り返す。

**why: 項目を 1 枚に全部並べると、探している項目まで画面を送ることになる。**
設定の画面を開く目的は、**1 つの項目を変えること**がほとんどで、
全部を読むことではない。

### 分類

| 分類 | 入る項目 |
| --- | --- |
| 接続 | エンジンの起動、起動するエンジン、接続するエンジン、接続方式 |
| エンジン | つないでいるエンジンの CPU とメモリ、資源の変え方の案内 |
| ログ | 読み込む行数、保持する行数、取り直す行数、ログの保存先 |
| 配色・言語 | 配色、画面の言語 |
| 設定ファイル | 設定ファイルの場所、読めなかった設定の場所、［既定に戻す］ |

**開いた直後は「接続」を選んだ状態にする。** 分類の一覧の一番上。

**分類を切り替えても、変えた設定は保存されている**（「保存」——変えた時点で保存する）。
分類を移る前に保存する操作は要らない。

### 「エンジン」は設定ではない

**「エンジン」の分類に置くのは、表示と案内だけで、変えられる項目は無い。**

**why: 利用者が資源を見たくなるのは、変えたいとき。**
変え方を探しに来る場所は設定の画面なので、変えられなくても設定の画面に置く
（「エンジンの資源」を参照）。

## 設定の項目

### 接続

| 項目 | 選べる値 | 既定 | 決めている仕様 |
| --- | --- | --- | --- |
| エンジンの起動 | 自動で起動する / ボタンを押したら起動する | 自動で起動する | `connection.md` の「設定で切り替える」 |
| 起動するエンジン | 候補から**複数**選ぶ | 接続するエンジンだけ | 「起動するエンジンと、接続するエンジン」 |
| 接続するエンジン | 最後につないだエンジン / 候補から **1 つ**選ぶ | 最後につないだエンジン | 「起動するエンジンと、接続するエンジン」 |
| 接続方式 | 自動 / ソケット / 子プロセス | 自動 | `connection.md` の「接続方式を選ぶ」 |
| ソケットのパス | 文字 | 空 | 接続方式が「ソケット」のときだけ入力できる |
| 実行するコマンドと引数 | 文字 | 空 | 接続方式が「子プロセス」のときだけ入力できる |

**接続方式が「自動」のときは、パスとコマンドの入力欄を押せない状態にする。**
入力できるのに使われない欄があると、利用者は**入力したのに使われない**と考える。

#### 起動するエンジンと、接続するエンジン

**起動と接続は別の設定にする。**

| 設定 | 選べる数 | 何を決めるか |
| --- | --- | --- |
| 起動するエンジン | **複数** | アプリを開いたときに起動を始めるエンジン |
| 接続するエンジン | **1 つ** | 起動が終わった後に繋ぐエンジン |

**why: 起動と接続は別の目的。** 起動は「あとで使うエンジンを、待たずに済むよう先に立ち上げておく」ため。
接続は「いま見たいコンテナのエンジンを選ぶ」ため。
**1 つにまとめると、繋がないエンジンを先に起動しておけない。**

**接続するエンジンは、起動するエンジンからチェックを外せない状態にする。**
外すと、停止したままのエンジンに繋ごうとして必ず失敗する。

**「エンジンの起動」が「ボタンを押したら起動する」のときは、起動するエンジンを選べない状態にする。**
自動で起動しない設定なので、選んでも使われない。

**接続するエンジンが「最後につないだエンジン」のときも、起動するエンジンは選べる。**
接続先が回ごとに変わっても、**先に起動しておきたいエンジンは変わらない。**

**DockerGUI が同時に繋ぐエンジンは、常に 1 つ**（`connection.md` の「接続するのは 1 つだけ。起動は複数できる」）。
起動が複数になっても、繋ぐ先は 1 つ。

**選んだエンジンが見つからないときは、状態バーを「選択待ち」にする**（`connection.md` の「選択待ち」）。
勝手に別のエンジンへ繋ぐと、**利用者にはコンテナが消えたように見える。**

### エンジンの資源

**つないでいるエンジンに割り当てられている CPU とメモリを表示する。**
`GET /info` の `NCPU` と `MemTotal` から取る（開発機で確認。`4 CPU / 6197440512 bytes` が返った）。

**DockerGUI から資源を変更しない。** 変える手段を**コピーできる形**で出すだけにする。

#### 変えたい値を入れると、コマンドが組み上がる

```
            ┌──────────┬───────────────────────────────┐
分類の一覧  │ 接続               │ つないでいるエンジン   colima                    ［コピー］  │
            │ エンジン           │ CPU                    4          →  [ 6  ]                 │
            │ ログ               │ メモリ                 5.8 GB     →  [ 12 ] GB              │
            │ 設定ファイル       │                                                              │
            │                    │ 変えるには                                                   │
            │                    │   colima stop && colima start -c 6 -m 12  ［コピー］         │
            └──────────┴───────────────────────────────┘
```

**入力した値でコマンドを組み直す。** DockerGUI はコマンドを実行しない。

**why: 決め打ちの例を出すと、利用者はコピーした後に数字を直すことになる。**
直し忘れると、**望んでいない値でエンジンが起動する。**

**入力欄の初期の値は、いまの値にする。** 変えたい側だけを直せばよい。

#### 環境ごとに出すもの

| 環境 | 出すもの | 確かめたか |
| --- | --- | --- |
| colima | `colima stop && colima start -c 6 -m 12` と ［コピー］ | **開発機で確認**（設定は `~/.colima/default/colima.yaml`） |
| Docker Desktop | **案内の文だけ。** `Docker Desktop の設定の画面で変えてください` | **確かめていない**（開発機に無い） |
| WSL2 | `.wslconfig` に設定する値と ［コピー］、あわせて `wsl --shutdown` の案内 | **確かめられない**（Windows の環境が無い） |

**Docker Desktop には入力欄を出さない。** 組み上げるコマンドが無いので、
入力させても使い道が無い。

**WSL2 で出すのは、コマンドではなく設定ファイルに書く値。**

```
%UserProfile%\.wslconfig に次の値を設定して、wsl --shutdown を実行してください

[wsl2]
processors=6
memory=12GB
```

**環境が表に当てはまらないときは、案内を出さない。**
CPU とメモリの表示だけにする。

#### エンジンにつないでいないとき

**CPU とメモリと入力欄と案内を、すべて出さない。**
資源はエンジンに問い合わせて取るので、繋いでいなければ値が無い。

**代わりに、次に何をすればよいかを出す。**

```
            ┌──────────┬───────────────────────────────┐
分類の一覧  │ 接続               │ Docker エンジンに接続していません                            │
            │ エンジン           │                                                              │
            │ ログ               │ CPU とメモリは、接続しているエンジンから取得します。         │
            │ 設定ファイル       │ 状態バーからエンジンを起動するか、接続してください。         │
            │                    │                                                              │
            │                    │ 起動の仕方は、設定の「接続」で決められます。                 │
            └──────────┴───────────────────────────────┘
```

**why: 何も出さないと、利用者は設定の画面が壊れていると考える**
（`common.md` の「1 件も無いとき」——空の画面に説明が無いと、利用者はアプリが壊れていると考える）。

**エンジンを起動するボタンは、設定の画面に置かない。**
エンジンの起動と接続は状態バーが受け持つ（`connection.md`）。
**同じ操作を 2 箇所に置くと、片方だけ状態が変わったときに食い違う。**

#### 資源を DockerGUI から変更しない why

**資源は Engine API に無い。** エンジンではなく、**エンジンを動かしている仮想マシン**の設定で、
環境ごとに置き場所も変え方も違う。

**Windows の 2 つの経路を検証できない**（`design-policy.md` の前提になる制約）。
`.wslconfig` の書き方を間違えると **WSL が起動しなくなり、Docker も起動しなくなる。**
開発者は Windows を持っていないので、**壊れたことに気づけるのは利用者だけになる。**

**影響が大きいことは、機能を出さない理由にならない。** 影響が大きいだけなら、確認を挟めば足りる。
**資源の変更を出さない理由は別で、
環境ごとに手段が違い、失敗を検証できない**ため。

**案内は出す。** DockerGUI が実行できないことでも、
**利用者が次にすることをコピーできる形で出せば役に立つ**
（`connection.md` の「診断」と同じ考え方）。

### ログ

| 項目 | 入れられる値 | 既定 | 決めている仕様 |
| --- | --- | --- | --- |
| 開いた直後に読み込む行数 | 100 〜 10000 | 1000 | `logs.md` の「開いた直後に読み込む行数」 |
| 画面が保持する行数 | 1000 〜 100000 | 10000 | `logs.md` の「行数の上限」 |
| 取り直す行数 | 1000 〜 20000 | 5000 | `logs.md` の「行数の上限」 |
| ログの保存先 | フォルダ | OS のダウンロードの場所 | `logs.md` の「ファイルに保存」 |

**上限と下限は、確かめて決めた値ではない。**
実際に何行で画面が固まるかは、機械の速さとログの 1 行の長さで変わる。
**実装のときに、長いログで確かめて決め直す。**

**「画面が保持する行数」は「開いた直後に読み込む行数」より小さくできない。**
小さくすると、開いた直後に読み込んだ行がその場で捨てられる。

### 配色・言語

| 項目 | 選べる値 | 既定 | 決めている仕様 |
| --- | --- | --- | --- |
| 配色 | OS に合わせる、ライト、ダーク | OS に合わせる | `common.md` の「配色を選ぶ」 |
| 画面の言語 | 自動、日本語、English | 自動 | `common.md` の「言語を選ぶ」 |

**「OS に合わせる」を選ぶと、状態バーの配色のボタンを一度も押していない状態に戻す。**
その後に状態バーのボタンを押すと、「ライト」か「ダーク」を選んだことになる。

**画面の言語の名前は、状態バーのメニューと同じく、その言語で表示する**（「日本語」「English」。`common.md` の「言語を選ぶ」）。

## 変えた設定が適用されるとき

**変えた時点で適用する。** すぐに適用できない項目だけ、いつ適用されるかを項目の下に表示する。

| 項目 | いつ適用されるか |
| --- | --- |
| 接続方式、ソケットのパス、実行するコマンドと引数 | **すぐ。** 接続し直す（`connection.md` の「切り替え中」） |
| 画面が保持する行数、取り直す行数 | **すぐ。** 開いているログの画面にも適用する |
| エンジンの起動、起動するエンジン | **次にアプリを開いたときから。** エンジンの起動は、アプリを開いた時にしか行わない |
| 接続するエンジン | **次にアプリを開いたときから。** いま接続しているエンジンは切り替えない。すぐ切り替えたいときは、状態バーの ［切り替える］ を使う |
| 開いた直後に読み込む行数 | **次にログの画面を開いたときから。** 開いている画面は読み込みが終わっている |
| ログの保存先 | **次に保存するときから** |
| 配色、画面の言語 | **すぐ。** 開いているすべての画面に適用する |

**「次に〜から」の項目には、いつ適用されるかの文を項目の下に出す。**
設定を変えたのに何も起きないと、利用者は設定が壊れていると考える。

## 保存

**変えた時点で保存する。保存のボタンは置かない。**

**why: 設定の項目が少なく、1 つずつ独立している。**
まとめて保存する形にすると、**保存を押さずに画面を離れた利用者の変更が消える。**

| 項目 | 内容 |
| --- | --- |
| 保存先 | OS ごとのアプリの設定の場所（macOS は `~/Library/Application Support/DockerGUI/`） |
| 形式 | JSON。利用者が読んで直せる形にする |
| 設定ファイルの場所 | **「設定ファイル」の分類に出し、［コピー］ を置く**（`common.md` の「利用者がコピーして使いたい値」） |

### 秘密を保存しない

**レジストリのログインの情報を、DockerGUI の設定ファイルに保存しない。**
取得のときは `~/.docker/config.json` を読む（`images.md` の「ログインが要るレジストリ」）。

**why: 保存する場所が増えるほど、漏れる場所が増える。**
Docker CLI がすでに持っているものを、DockerGUI が写して持つ必要が無い。

## 入力が正しくないとき

**保存しない。入力欄の下に、正しくない理由を出す。**

```
画面が保持する行数   [ 50 ]
1000 以上 100000 以下の数を入れてください
```

**入力欄の値は、利用者が入れたまま残す。** 直せるようにするため。
**前の値に戻さない**——何を入れたのか分からなくなる。

## 既定に戻す

［既定に戻す］ を押すと、すべての項目を既定の値に戻す。

```
┌──────────────────────────────────┐
│ すべての設定を、既定の値に戻します。                               │
│ 元に戻せません。                                                   │
│                              [ やめる ]  [ 既定に戻す ]            │
└──────────────────────────────────┘
```

**配色と画面の言語は、既定に戻さない。** どちらも、「配色・言語」で 1 つずつ選んで変える。
［既定に戻す］ を押すのは、変えた設定のせいで動きがおかしくなったときで、配色と画面の言語は動きに関わらない（`common.md` の「言語を選ぶ」）。

**画面の切り替え（タグの無いイメージを出すなど）も、あわせて既定に戻す。**
設定の画面に出していない項目も覚えているので、**戻す対象から外すと、
「既定に戻した」のに画面が元のままになる。**

## 設定ファイルを読めないとき

**アプリを開いたときに設定ファイルを読むので、設定の画面は開いていない。**
知らせを設定の画面に出すと、設定の画面を開くまで誰も気づかない。

**状態バーに出す**（`common.md` の「画面の構成」——画面全体に関わる知らせは状態バーに出す）。

```
            ┌──────────────────────────────────────────┐
状態バー    │ 接続先: colima                                                                     │
            │ 設定を読めませんでした。既定の値で動いています    ［設定を開く］［閉じる］         │
            ├──────────────────────────────────────────┤
対象の一覧  │ コンテナ                                                                           │
            │ イメージ                                                                           │
            └──────────────────────────────────────────┘
```

**接続の状態の下に、行を足して出す。** 接続の状態を押しのけない——
Docker につながっていないほうが、利用者にとって先に片付ける問題になる。

**利用者が ［閉じる］ を押すまで消さない**（`common.md` の「結果の知らせ方」）。
アプリを開いた直後に出るので、**席を外していた利用者にも届く必要がある。**

### 場面ごとの振る舞い

| 場面 | 既定に戻す範囲 | 状態バーに出す文 |
| --- | --- | --- |
| 設定ファイルが無い | 全部 | **出さない。** 初めて起動したときは無いのが普通 |
| 設定ファイルが壊れている（JSON として読めない） | 全部 | `設定を読めませんでした。既定の値で動いています` |
| 項目の値が範囲の外 | **範囲の外だった項目だけ**。他の項目は読んだ値を使う | `設定の「画面が保持する行数」を読めませんでした。既定の 10000 で動いています` |

**範囲の外の項目も知らせる。** 黙って既定に戻すと、
**利用者が書いた値で動いていると思い込んだまま使い続ける。**

**範囲の外の項目が 2 つ以上あるときは、項目の名前を並べて 1 行にまとめる。**
項目ごとに行を増やすと、状態バーが知らせで埋まる。

### 状態バーに出す知らせのボタン

| 押すボタン | 何をするか |
| --- | --- |
| ［設定を開く］ | **設定の画面を開く。** 利用者が最初にするのは、設定を入れ直すこと |
| ［閉じる］ | 知らせを消す。次にアプリを開いたときに、また読めなければまた出る |

**［設定を開く］ で、どの分類を選んだ状態にするかを決める。**

| 読めなかったもの | 選んだ状態にする分類 |
| --- | --- |
| 1 つの項目 | **読めなかった項目が入っている分類**（例: 「画面が保持する行数」なら「ログ」） |
| 2 つ以上の項目で、分類が同じ | 同じ分類 |
| 2 つ以上の項目で、分類が違う | **「設定ファイル」**。どの分類を開いても片手落ちになる |
| 設定ファイル全体（JSON として読めない） | **「設定ファイル」**。読めなかった設定の場所を出す分類 |

**why: 分類を選ばせると、利用者は読めなかった項目を分類から探すことになる。**
知らせの文には項目の名前が出ているので、**開いた先に同じ項目が見えていないと、
知らせと画面がつながらない。**

**OS のファイルの画面は開かない。** 設定の画面に設定ファイルの場所を出してあるので
（「保存」を参照）、ファイルを直したい利用者は設定の画面からたどれる。

### 壊れた設定ファイルを、上書きする前に残す

`settings.json` を `settings.json.broken` に変えてから、既定の設定を書く。

**why: 利用者が手で直した設定が壊れていることがある。**
黙って上書きすると、何を書いていたか分からなくなる。

**残したファイルがあるときは、「設定ファイル」の分類にも場所を出す。**

```
設定ファイル       ~/Library/Application Support/DockerGUI/settings.json        ［コピー］
読めなかった設定   ~/Library/Application Support/DockerGUI/settings.json.broken ［コピー］
```

**why: 残しただけでは、利用者は `settings.json.broken` があることに気づけない。**
設定の画面に出せば、書いていた値を自分で読み直せる。

## 設定の画面の状態

| 状態 | 表示する内容 | ボタン |
| --- | --- | --- |
| 表示中 | 設定の項目 | ［選択］［コピー］［既定に戻す］ |
| 入力が正しくない | 正しくない入力欄の下に、理由 | ［選択］［コピー］［既定に戻す］ |

| 状態 | どうやってその状態になるか |
| --- | --- |
| 表示中 | 左の一覧の「設定」を選んだ |
| 入力が正しくない | 数の欄に、範囲の外の値を入れた |

**「設定を読めなかった」は、設定の画面の状態ではない。**
アプリを開いたときに起きて、状態バーに出る（「設定ファイルを読めないとき」）。
設定の画面を開いているかどうかに関わらず出る。

**状態遷移図は描かない。** 状態が 2 つで、互いに行き来するだけなので、表で読める。
