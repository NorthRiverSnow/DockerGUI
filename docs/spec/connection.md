# 仕様: 接続と診断

`common.md` の約束を前提にする。

## 接続先を探す

**アプリを開くたびに探索し直すことはしない。** 一度つながった接続先を保存し、次回は保存された接続先を使う。

### 探す順序

保存された接続先があれば、まず保存された接続先を試す。
保存された接続先で失敗した場合と、保存が無い場合に、次の順で探す。

**macOS**

1. `docker context ls` で現在のコンテキストのエンドポイントを取得し、そこへつなぐ
2. 取得できなければ `/var/run/docker.sock` へつなぐ

**why: macOS には colima のように `/var/run/docker.sock` を使わない構成がある。**
決め打ちにすると、colima のような構成ではつながらない。

**Windows**

1. `docker.exe` があれば、`docker context ls` で名前付きパイプを取得し、そこへつなぐ
2. `docker.exe` が無い、または 1 で失敗した場合、`wsl.exe -l -q` でディストロの一覧を取得する
3. 各ディストロで `docker version` を試し、**最初に成功したディストロ**を接続先にする

**why: WSL のディストロにだけ Docker を入れた構成では、Windows 側に `docker.exe` が存在しない。**
Windows 側に `docker.exe` が無い構成では、`docker context ls` の手順を実行できない。

### 探索には時間がかかる

ディストロの数だけ `docker version` を試すため、探索は数十秒におよぶことがある。
探索の最中に状態バーへ出すものは、「接続の状態」で定める。

## 接続の状態

状態バーは常に見える。状態によって、出す内容が変わる。

**1 行目は接続先のエンジンについて出す。** 2 行目は、DockerGUI が接続していない別のエンジンが
動作しているか、起動の途中であるときだけ出す（「起動しているが、接続していないエンジン」）。

| 状態 | 表示する内容 | ボタン |
| --- | --- | --- |
| 探索中 | 試しているエンジンの名前、実行しているコマンド、経過した時間 | ［中止］ |
| 選択待ち | 接続するエンジンを選択するよう求める文、候補のエンジンの名前 | 候補ごとに、エンジンの名前のボタン（例: ［colima］［Docker Desktop］） |
| 起動中 | エンジンの名前、実行しているコマンド、経過した時間 | ［中止］ |
| 接続中 | エンジンの名前、実行しているコマンド、経過した時間 | ［中止］ |
| 接続済み | エンジンの名前 | ［停止］ |
| 切り替え中 | 切り替え元と切り替え先のエンジンの名前、経過した時間 | ［中止］ |
| 動作中・未接続 | エンジンの名前、動作していること | ［切り替える］（別のエンジンに接続している場合）／［接続］（どのエンジンにも接続していない場合） |
| 停止中 | エンジンの名前、停止していること | ［起動］ |
| 接続不可 | エンジンの名前、失敗の原因 | ［診断を開く］［接続方式を選択］ |
| 再接続待ち | エンジンの名前、次に再接続するまでの残り時間 | ［今すぐ再接続］［あきらめる］ |
| 再接続中 | エンジンの名前、実行しているコマンド、経過した時間 | ［中止］ |

```
Ubuntu-22.04 を試しています…（wsl.exe -d Ubuntu-22.04 -e docker version）  経過 00:03  ［中止］
接続するエンジンを選択してください                                  ［colima］［Docker Desktop］
colima を起動しています…（colima start）                                   経過 00:08  ［中止］
colima に接続しています…                                                   経過 00:02  ［中止］
接続先: colima                                                                          ［停止］
colima から Docker Desktop に切り替えています…                             経過 00:02  ［中止］
Docker Desktop は動作しています                                                   ［切り替える］
colima は動作しています                                                                 ［接続］
colima は停止しています                                                                 ［起動］
colima に接続できません（応答がありません）                     ［診断を開く］［接続方式を選択］
colima との接続が切れました。18 秒後に再接続します                ［今すぐ再接続］［あきらめる］
colima に再接続しています…（docker system dial-stdio）                     経過 00:02  ［中止］
```

状態バーの書き方は、`common.md` の「待たせるときの表示」に従う。

**1 行目に出す状態の表のボタンは、画面の言語を選ぶボタンの左に並べる。** 画面の言語を選ぶボタンは、
接続の状態によらず状態バーの 1 行目の右端に置く（`common.md` の「言語を選ぶ」）。表示の例では省いている。

「動作中・未接続」は、［切り替える］ と ［接続］ のどちらを出すかで表示の例を 2 行に分けている。

### 「選択待ち」

接続先が保存されておらず、候補のエンジンが複数あるときに、この状態で待つ
（「接続するのは 1 つだけ。起動は複数できる」の、どれに繋ぐかの表）。**候補ごとに、エンジンの名前をボタンにして並べる。**

| 押したボタンのエンジン | 次の状態 |
| --- | --- |
| 動作している | 接続中 |
| 停止している | 起動中。起動が終わったら接続中 |

**押したエンジンを接続先として保存する。** 次にアプリを開いたときは、保存した接続先に繋ぐので、
もう一度選ばせることはしない。毎回同じエンジンに繋ぎたい利用者は、設定で接続するエンジンを選べる
（`settings.md` の「起動するエンジンと、接続するエンジン」）。

### 「接続中」と「起動中」を分ける

エンジンが起動し終わっても、DockerGUI の接続はまだ終わっていない——
Engine API の版を決め、最初の一覧を取得するまでに時間がかかる。
接続先が WSL のディストロの場合、子プロセスの起動を挟むので、さらに時間がかかる。

**why: 状態を分けないと、どちらで止まっているのか利用者に分からない。**
エンジンの起動が遅いのか、接続が応答しないのかで、次に試すことが変わる。

### ［中止］を押した後の状態

**［中止］を押した後は「接続不可」にしない。** 中止した後の状態は、
エンジンが動いているかどうかで決める。

| 中止した時点のエンジン | 中止した後の状態 | ボタン |
| --- | --- | --- |
| 動いていない | 停止中 | ［起動］ |
| 動いている | 動作中・未接続 | ［接続］ |

**why: 中止は失敗ではない。** 「接続不可」は DockerGUI が試したうえで失敗した状態で、
［診断を開く］を出す。中止した利用者に診断を出しても、調べるものが無い。
中止した後も**あとから手動で接続を始められる状態**にしておく。

**DockerGUI は自動で次の候補を試さない。** 中止した理由は利用者しか知らないので、
利用者がボタンを押すまで待つ。

#### ［中止］はエンジンを止めない

「接続中」で ［中止］ を押しても、**DockerGUI が接続をやめるだけで、エンジンは動いたまま**になる。
エンジンを止めたい利用者は、接続してから ［停止］ を押す。

**why: エンジンは DockerGUI が起動したものとは限らない。** 利用者が自分で起動していたエンジンを、
接続をやめるつもりの操作で止めてしまうと、DockerGUI の外で動いているコンテナも止まる。

「起動中」で ［中止］ を押した場合は、**起動のコマンドを止めるので、エンジンは起動しない。**

#### 起動のコマンドを止めた後は、状態を確かめ直す

`colima start` のようにエンジンを起動するコマンドは、途中で止めると
**仮想環境が中途半端な状態で残ることがある。** 完全に停止しているとは限らない。

そのため、中止した後は**エンジンが動いているかどうかを確かめてから**、
「停止中」と「動作中・未接続」のどちらにするかを決める。

**接続先の切り替えを中止した場合は、切り替える前の接続先に戻す。**
切り替える前の接続先は動いているので、戻せる。戻せなかった場合は、「［中止］を押した後の状態」の表のとおりにする。

### 接続していないエンジンの状態は、定期的に確かめる

利用者が DockerGUI の外でエンジンを起動することがある（ターミナルで `colima start` を実行する、
Docker Desktop を開く）。**DockerGUI は起動を検知して、状態の表示を切り替える。**

**`/events` は接続しているエンジンからしか届かない。**
接続していないエンジンが起動したことを知らせる仕組みは存在しないため、
**接続していないエンジンについては、DockerGUI から定期的に確かめに行く。**

確かめ方は接続方式によって負荷が違うので、間隔を分ける。

| 接続方式 | 確かめ方 | 負荷 | 間隔 |
| --- | --- | --- | --- |
| ソケット、名前付きパイプ | ソケットがあるかを調べ、あればつないで `GET /_ping` を送る | 軽い | 5 秒 |
| 子プロセス | `wsl.exe` を起動して `docker version` を実行する | 重い | 30 秒 |

**why: 子プロセスの経路は、確かめるたびに `wsl.exe` の起動を挟む。**
短い間隔で繰り返すと、利用者の機械の資源を DockerGUI が使い続けることになる。

**確かめた結果で、状態の表示が変わる。**

| 確かめる前 | エンジンが起動していた場合 |
| --- | --- |
| 停止中 | 動作中・未接続（［接続］が出る） |
| 接続不可 | 動作中・未接続（［接続］が出る） |

**自動では接続しない。** 状態の表示を変えて、［接続］を出すところまでにする。

**why: 利用者が DockerGUI 以外の目的でエンジンを起動したのかもしれない。**
起動を検知しただけで繋ぎに行くと、利用者が意図していない接続が始まる。

### 起動しているが、接続していないエンジン

エンジンが起動していても、DockerGUI がそのエンジンに接続しているとは限らない。
**DockerGUI が接続していないエンジンのうち、動作しているものと起動の途中のものは、状態バーの 2 行目に出す。**

| 2 行目に出すエンジンの状態 | 表示する内容 | ボタン |
| --- | --- | --- |
| 動作中・未接続 | エンジンの名前、動作していること | ［切り替える］ |
| 起動中 | エンジンの名前、実行しているコマンド、経過した時間 | ［中止］ |

```
接続先: colima                                              ［停止］
Docker Desktop は動作しています                       ［切り替える］
```

```
接続先: colima                                              ［停止］
Docker Desktop を起動しています…            経過 00:12  ［中止］
```

2 行目の「起動中」が出るのは、設定の「起動するエンジン」で選ばれたエンジンのうち、
接続しないエンジンが起動の途中のとき（「接続しないエンジンの起動は、待たない」）。起動が終わると「動作中・未接続」に変わり、
［切り替える］ が出る。**起動の途中のエンジンには ［切り替える］ を出さない。**
切り替えても、起動が終わるまで接続できない。

#### 2 行目に出すエンジンの決め方

**1 行目に名前が出ていないエンジンのうち、「動作中・未接続」と「起動中」のものを出す。**

| 状態 | 1 行目に名前が出るエンジン | 2 行目に出るエンジン |
| --- | --- | --- |
| 切り替え中 | 切り替え元と切り替え先の 2 つ | 残りのエンジンのうち、動作しているものと起動の途中のもの |
| それ以外の状態 | 対象のエンジン 1 つ | 残りのエンジンのうち、動作しているものと起動の途中のもの |

**why: 同じエンジンを 1 行目と 2 行目の両方に出すと、別のエンジンが 2 つあるように見える。**
「切り替え中」は、切り替え元と切り替え先の両方が 1 行目に出るので、
2 行目にはどちらも出さない。

**エンジンが 2 つあって、1 つに接続していれば、状態バーは常に 2 行になる。**
接続できている間も 2 行目を出す——別のエンジンが起動していることは、
接続できているかどうかに関わらず、利用者が知りたい事実であるため。

2 行目に出るエンジンが 2 つ以上ある場合は、エンジンごとに 1 行ずつ並べ、
それぞれの行に、エンジンの状態に応じたボタンを置く。

### 切断されたとき

**「切断された」とは、一度つながったあとに接続が失われた状態を指す。**
まだ一度もつながっていない状態は「接続不可」で、別の状態として扱う。

| 状態 | つながったことがあるか |
| --- | --- |
| 接続不可 | ない（起動した直後、接続先を切り替えた直後） |
| 切断された（再接続待ち・再接続中） | ある |

#### 切断の原因は、切れた時点では分からない

| 原因 | エンジンの状態 |
| --- | --- |
| 利用者が DockerGUI の外でエンジンを停止した | 停止している |
| PC がスリープから復帰した | 仮想環境が止まっていることがある |
| WSL のディストロが終了した | 停止している |
| 通信路にしている子プロセスが終了した | 起動している |
| DockerGUI の不具合でストリームが閉じた | 起動している |

**DockerGUI から見えるのは「通信路が切れた」ことだけで、原因は分からない。**
そのため、原因を調べてから動くのではなく、**まず再接続を試みて、その結果で原因を判別する。**
つながればエンジンは動いていたと分かり、つながらずエンジンが停止していると分かれば
「停止中」の状態へ移る。

#### 再接続の繰り返し

**自動で再接続を試みる。** 間隔を空けて繰り返し、繰り返すたびに間隔を延ばす。

繰り返しの間、状態は 2 つを行き来する。

| 状態 | 利用者が押せるもの |
| --- | --- |
| 再接続待ち | ［今すぐ再接続］で待ち時間を飛ばす。［あきらめる］で繰り返しをやめる |
| 再接続中 | ［中止］で、いま試している接続をやめる |

**why: 待っている間と試している間で、押せて意味のあるものが違う。**
再接続を試している最中に［今すぐ再接続］を出しても、すでに試しているので押す意味が無い。
逆に待っている間は、間隔が延びて数十秒待つことがあるため、待ち時間を飛ばせると役に立つ。

**［あきらめる］を押すと自動の再接続をやめ、「［中止］を押した後の状態」と同じ扱いにする。**
**［中止］を押した場合は「再接続待ち」に戻り、自動の再接続は続く。**
利用者が止めたいのは、1 回の試行なのか繰り返し全体なのか、区別がつかないため、
押せるものを分けて両方を用意する。

再接続に成功したら、**開いていた画面を閉じずに**一覧を取り直す。

**ログの画面とターミナルの画面では、扱いが違う。**

| 画面 | 再接続したとき |
| --- | --- |
| ログ | **開いたまま。** 通信路だけを張り直し、切れていた区間に省略の知らせを差し込む（`logs.md`） |
| ターミナル | **画面は開いたまま、セッションを開き直す。** 切れた時点で、コンテナの中で実行していたコマンドが終わっている（`terminal.md`） |

**why: ログは切れた前後を続けて読むもので、画面を閉じると読んでいた位置が失われる。**
エンジンに原本が残っているので、切れていた区間はあとから取り直せる。
ターミナルは切れた時点でコマンドが終わっているため、セッションを開き直す以外にできることが無い。
それまでの出力は残す（`terminal.md` の「出力は消さない」）。

**再接続は試みるが、エンジンの起動は試みない。**
再接続を繰り返してもつながらず、エンジンが停止していると分かった場合は、
起動のボタンを出す（「実行中に切断されたときは、自動で起動しない」）。

## エンジンが停止しているとき

接続先は見つかったが、Docker のエンジンが動いていない場合の扱い。

### 起動する手段

| 環境 | 停止していると分かる条件 | 起動するコマンド |
| --- | --- | --- |
| colima（macOS） | `colima status` が失敗する | `colima start` |
| Docker Desktop（macOS） | ソケットにつながらず、アプリも起動していない | Docker Desktop を開く |
| Docker Desktop（Windows） | 名前付きパイプにつながらない | Docker Desktop を開く |
| WSL のディストロの中の Docker | ディストロの中で `docker version` が失敗する | `sudo service docker start` |

**WSL のディストロの中の Docker は、起動できないことがある。** `sudo` がパスワードの入力を
求める設定になっていると、アプリからは入力できない。
**`sudo` がパスワードを求める場合は、案内だけに切り替える**
（「起動する手段が分からないとき」と同じ扱い）。

### 既定は自動で起動する

アプリを開いたときと、利用者が接続先を切り替えたときに、停止を検出したら**利用者に聞かずに起動する**。

状態バーに、次の 3 つを出す。

```
colima を起動しています…（colima start）  経過 00:18   ［中止］
```

- **実行しているコマンド。** 何が起きているかが分からないまま数十秒待たされない
- **経過した時間。** colima と Docker Desktop は仮想環境を起動するので数十秒かかる
- **中止のボタン**

起動が終わったら、**利用者の操作を待たずに接続する。**

### 接続するのは 1 つだけ。起動は複数できる

**DockerGUI は同時に 1 つのエンジンにしか繋がない。**
一方、**起動は複数のエンジンに対して行える**（`settings.md` の
「起動するエンジンと、接続するエンジン」）。

| | 数 | 決め方 |
| --- | --- | --- |
| 起動するエンジン | **複数** | 設定で選ぶ。選んでいなければ、接続するエンジンだけ |
| 接続するエンジン | **1 つ** | 次の表のとおり |

**why: 繋がないエンジンでも、先に起動しておきたい。**
エンジンの起動には数十秒かかるので、**あとで切り替える先を先に立ち上げておけば、
切り替えのときに待たずに済む。**

どれに繋ぐかは、次のとおり。

| 状況 | どうするか |
| --- | --- |
| **設定で接続するエンジンを選んである** | **選ばれたエンジンに繋ぐ。停止していれば起動する** |
| 接続先が保存されていて、保存されたエンジンが停止している | 保存されたエンジンを起動する |
| 接続先が保存されておらず、候補が 1 つ | 見つかった 1 つの候補を起動する |
| **接続先が保存されておらず、候補が複数** | **起動しない。どれに繋ぐかを選ばせる** |

**why: どのエンジンに繋ぐかで、見えるコンテナが丸ごと変わる。**
しかも起動には数十秒かかるので、DockerGUI が勝手に選ぶと、利用者は
「意図しないエンジンの起動を待たされた末に、見たかったコンテナが 1 つも無い」状態になる。
「自動で起動する」設定を選んでいても、候補が複数のときだけは選ばせる。

**毎回同じエンジンを使う利用者は、設定で接続するエンジンを選べる**
（`settings.md` の「起動するエンジンと、接続するエンジン」）。
選んであれば、候補が複数でも選ばせない。

### 接続しないエンジンの起動は、待たない

**接続するエンジンの起動が終わったら、他のエンジンの起動を待たずに接続する。**

起動が終わっていないエンジンは、状態バーの 2 行目に「起動中」で出し、起動が終わったら
「動作中・未接続」に変える（「起動しているが、接続していないエンジン」）。

**why: 接続を待たせる理由が無い。** 他のエンジンを起動するのは後で切り替えるためで、
**いま見たいコンテナは、接続するエンジンの中にある。**

### 別のエンジンが起動している場合

保存された接続先が停止していて、**別のエンジンはすでに起動している**ことがある。
別のエンジンが起動していても、**保存された接続先を起動する。勝手に切り替えない。**

**why: エンジンが違えばコンテナも違う。** 黙って別のエンジンに繋ぐと、
利用者には「コンテナが消えた」と見える。

起動を待つ間、待たずに済む道を状態バーに示す（「起動しているが、接続していないエンジン」）。
**切り替えるかどうかは利用者が決める。**

### 実行中に切断されたときは、自動で起動しない

アプリを使っている最中にエンジンが停止した場合は、**自動で起動せず、ボタンを出す。**

**why: 利用者が自分で停止させた可能性が高い。** 起動した直後の停止は「まだ起動していなかった」だが、
使っている最中の停止は「たった今、誰かが止めた」であって、意味が違う。

### 起動に失敗したとき

状態バーに、**実行したコマンドと、標準エラー出力の内容**を出す。［診断を開く］を置く。

**自動では再試行しない。** 同じコマンドを繰り返しても、同じ失敗を繰り返すだけになる。

### 起動する手段が分からないとき

「起動する手段」の表に当てはまらない環境では、**起動を試みない。**
「停止中」の状態にして、［起動］ を出さない。利用者は、自分の環境で使うコマンドで起動する。

### 設定で切り替える

**エンジンを自動で起動するかどうかは、設定で変えられる**（`settings.md` の「接続」）。

「ボタンを押したら起動する」を選んだ場合、停止を検出しても起動せず、「停止中」の状態にする。

```
colima は停止しています                      ［起動］
```

### エンジンを停止する

接続しているエンジンを、DockerGUI から停止できる。

利用者がエンジンを停止したい場面は日常的にある——作業を終えて電池とメモリを節約する、
他の重い作業のために資源を空ける、エンジンの設定を変えたので起動し直す、など。

#### 停止できるのは、接続しているエンジンだけ

［停止］は状態バーに置く。状態バーが表しているのは接続しているエンジンなので、
停止の対象も接続しているエンジンになる。

**接続していないエンジンには、［停止］を出さない。**
「起動しているが、接続していないエンジン」の行には、［停止］ を置かない。

**why: 接続していないエンジンのコンテナは、DockerGUI の画面に出ていない。**
停止の確認で「止まるコンテナの名前」を並べられないので、
利用者は何が止まるか分からないまま停止することになる。

#### 停止するコマンド

| 環境 | 停止するコマンド |
| --- | --- |
| colima（macOS） | `colima stop` |
| Docker Desktop（macOS と Windows） | Docker Desktop を終了する |
| WSL のディストロの中の Docker | `sudo service docker stop` |

`sudo` がパスワードを求める設定の場合、DockerGUI からは停止できない。
**停止のボタンを出さず、実行するコマンドを案内する**（起動のときと同じ扱い）。

#### 停止する前に、止まるコンテナを並べる

```
┌────────────────────────┐
│ colima を停止します。                          │
│ 動いているコンテナ 3 件も停止します。          │
│   web-1 / db-1 / redis-1                       │
│                                                │
│                      [ やめる ]  [ 停止する ]  │
└────────────────────────┘
```

**why: エンジンを停止すると、DockerGUI の外で起動したコンテナも止まる。**
別の作業で使っているコンテナが含まれていないかを、利用者が名前を見て判断できるようにする。
件数だけでは、何が止まるか分からない。

エンジンの停止は、取り返しのつかない操作ではない（また起動できる）。
それでも確認を挟むのは、**止まる範囲が DockerGUI の画面の外まで及ぶ**ため。

#### 停止したあと

状態バーに、停止していることと起動のボタンを出す。

```
colima は停止しています                      ［起動］
```

**利用者が DockerGUI から停止した直後に、DockerGUI が自動で起動し直すことはしない。**
「自動で起動する」設定を選んでいても、利用者が停止した直後は起動しない。

**why: 止めたいから止めたのに、すぐ起動し直すと止められない。**

## 接続方式を選ぶ

設定の画面で、接続方式を手で選べる。既定は「自動」。

| 選べる方式 | 入力するもの |
| --- | --- |
| 自動 | なし。「探す順序」のとおりに探す |
| ソケット | ソケットのパス、または名前付きパイプの名前 |
| 子プロセス | 実行するコマンドと引数 |

「子プロセス」は、**起動したコマンドの標準入出力を Docker との通信路として使う**方式。
Windows で WSL の中の Docker につなぐときに使う。

```
wsl.exe -d Ubuntu-22.04 -e docker system dial-stdio
```

**「子プロセス」の方式は macOS でも選べる。** macOS では次の形になる。

```
docker system dial-stdio
```

**why: Windows でしか使わない経路にすると、経路の誤りが Windows でしか表面化しない。**
macOS で同じ経路を選べるようにしておけば、開発機で先に気づける。

### 接続先を変えたとき

**開いているログとターミナルのストリームをすべて閉じてから、新しい接続先につなぐ。**
閉じないまま切り替えると、前の接続先のログが新しい接続先のものとして表示される。

ストリームを閉じてから新しい接続先につながるまでの間は、
状態バーを「切り替え中」にする。

**why: 切り替えの最中は、コンテナの一覧が空になる。** 状態を出さないと、
利用者には「コンテナが消えた」と見える。切り替え元と切り替え先の名前を並べて出せば、
一覧が入れ替わる途中だと分かる。

## 診断

左の一覧の「診断」から開く。**接続できているかどうかに関わらず、いつでも実行できる。**

### 実行する項目

上から順に実行し、結果を 1 つずつ表示する。**途中で失敗しても、残りを実行する**
——どこまでできているかが分かるため。

| 項目 | 確かめること |
| --- | --- |
| OS と版 | アプリが動いている環境 |
| `docker.exe` の有無 | Windows で名前付きパイプの経路を使えるか（macOS では `docker` の場所） |
| コンテキストの一覧 | どの接続先が候補になるか |
| ディストロの一覧（Windows のみ） | `wsl.exe -l -q` の結果 |
| 各ディストロの `docker version` | ディストロの中で Docker が動いているか |
| バイト列の往復（Windows のみ） | 既知のバイト列を送って、同じものが返るか |
| 疎通（`GET /_ping`） | Docker との通信が成立するか |
| `wslpath` の結果（Windows のみ） | Windows のパスを WSL のパスに変換できるか |

「バイト列の往復」は、**`wsl.exe` を通したときにバイト列が変化しないこと**を確かめる。
バイト列が変化すると、ログとターミナルの表示が壊れる。

### 表示するもの

各項目について、次の 3 つを出す。

- **実行したコマンドと引数**
- **標準出力の内容**
- **標準エラー出力の内容**

```
┌──────────────────────────────────────────┐
│ 診断                                               ［すべてコピー］                │
│                                                                                    │
│ 疎通（GET /_ping）                                                                 │
│   コマンド     docker system dial-stdio                      ［コピー］            │
│   標準出力     HTTP/1.1 200 OK                               ［コピー］            │
│   標準エラー （無し）                                                              │
│                                                                                    │
│ wslpath の結果                                                                     │
│   コマンド     wsl.exe -e wslpath -a C:\Users\me\app         ［コピー］            │
│   標準出力     /mnt/c/Users/me/app                           ［コピー］            │
│   標準エラー （無し）                                                              │
└──────────────────────────────────────────┘
```

### コピーの手段

| 押すボタン | 出す場所 | コピーされるもの |
| --- | --- | --- |
| ［すべてコピー］ | 診断の画面の先頭 | **全項目の結果**。項目の名前を付けた文字列 |
| ［コピー］ | コマンド・標準出力・標準エラー出力の右 | **左の値** |

中身が空の値（「表示するもの」の図の `（無し）`）には、アイコンを置かない。

`Cmd/Ctrl + C` は、文字を選んでいなければ ［すべてコピー］ と同じ働きをする
（`common.md` の「キーボードの操作」）。

コピーしたことの知らせ方は `common.md` の「コピーしたことを知らせる」と同じ。

**why: まとめてコピーできるようにする。** 開発者は Windows の環境を持っていないので、
手元で再現できない。利用者が貼り付けた診断の結果が、原因を切り分ける唯一の材料になる。
項目ごとにコピーさせると、貼り忘れが出る。

**why: 項目ごとのアイコンも置く。** 利用者が自分で調べるときは、
**コマンド 1 本だけをターミナルに貼り付けたい**場面がある。
まとめてコピーしかできないと、貼り付けてから要らない行を消すことになる。

### 秘密を出さない

診断の結果に、**環境変数の値とレジストリの資格情報を含めない。**
利用者は診断の結果をそのまま貼り付けるので、含めると本人が気づかないまま外に出る。
