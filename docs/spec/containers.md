# 仕様: コンテナ

`common.md` の約束を前提にする。

## 一覧

### 出す列

| 列 | 内容 |
| --- | --- |
| 選択 | チェックボックス（「まとめて操作する」） |
| 状態 | 「状態の呼び方」のとおり |
| 名前 | コンテナの名前 |
| イメージ | コンテナを作ったイメージの名前とタグ |
| ポート | 外に公開しているポートの対応（例: `8080 → 80`）。無ければ空。IPv4 と IPv6 で同じ対応を公開していても、1 つにまとめて出す |
| 時間 | 動作中のコンテナは起動してからの経過。動作中でないコンテナは終了してからの経過 |

**時間は、今からの経過で出す**（`common.md` の「表記」の「一覧の時刻」）。一度も起動していないコンテナは空にする。

コンテナ ID は一覧に出さない。**名前があるコンテナを ID で見分ける利用者はいない。**
ID は詳細の画面に出す。

### 列の幅

**どの列の幅も、行の中身が変わっても変えない。**

| 列 | 幅 | 収まらない文 |
| --- | --- | --- |
| 選択 | チェックボックスの幅 | 出ない |
| 状態、時間 | 出しうる文のうち、画面に描いたときにいちばん幅の広い文の幅（言語ごと） | 出ない |
| 名前、イメージ | 選択・状態・時間・操作の列の残りを、決まった割合で分ける | 中央を「…」にして、先頭と末尾を残す（`common.md` の「長い名前」） |
| ポート | 名前とイメージと同じ | 末尾を「…」にする |
| 操作 | 操作のボタンを、出しうるいちばん多い数だけ並べ、［詳細］ を加えた幅 | 出ない |

- **全文の見方:** 収まらない文は、マウスを重ねると全文を出す。
- **コピー:** 画面の裏には全文を持ち、選択してコピーすると全文が写る（`common.md` の「利用者がコピーして使いたい値」）。

状態と時間の列の幅は、文の字数ではなく、画面に描いた文の幅で決める（`common.md` の「文の長さは、言語によって変わる」）。
終了コードは 0 から 255 までなので、3 桁の終了コードの呼び方を幅に入れる。経過の年の数は 2 桁まで入れる（コンテナの経過が 100 年を超えることは無い）。数字は、どの数字も同じ幅で描く。

**why: 行の中身が変わるたびに列が横に動くと、目で追っている行や列を見失う。** 行の中身は、利用者が操作しなくても変わる。
状態は、健康状態とエンジンの出来事で変わる。時間は、時間が経つたびに変わる。ポートは、止まっているコンテナでは空になり（開発機で確認。エンジンは、止まっているコンテナの公開しているポートを返さない）、起動すると現れる。

### 状態の呼び方

Engine API が返す状態は英語で、そのまま出すと利用者が意味を調べることになる。
**日本語で表示するときは、日本語の言葉に置き換える。**
**英語で表示するときは、Docker の言葉の先頭を大文字にして出す**（`common.md` の「Docker の英語の言葉」）。

| Engine API が返す状態 | 日本語で出す言葉 | 英語で出す言葉 | コンテナは動いているか |
| --- | --- | --- | --- |
| `running` | 動作中 | `Running` | 動いている |
| `paused` | 一時停止中 | `Paused` | 止まっている（再開できる） |
| `restarting` | 再起動中 | `Restarting` | 起動し直している途中 |
| `created` | 未起動 | `Created` | 動いていない |
| `exited`（終了コード 0） | 正常終了 | `Exited (0)` | 動いていない |
| `exited`（終了コード 0 以外） | 終了（コード 143） | `Exited (143)` | 動いていない |
| `removing` | 削除中 | `Removing` | 動いていない |
| `dead` | 削除失敗 | `Dead` | 動いていない |

**再起動の方針**は、コンテナが終了したときに、エンジンが自動で起動し直すかどうかの設定で、`docker run --restart` や Compose の `restart:` で付ける（Docker の文書の「Start containers automatically」）。
**`restarting` は、エンジンが再起動の方針に従って、終了したコンテナを自動で起動し直している間の状態。**
［再起動］ を押しても、`restarting` にはならない（「再起動は、停止してから起動する」）。

**`running` は、健康状態でさらに呼び分ける**（「動作中のコンテナは、健康状態で呼び分ける」）。
**`created` は起動の失敗を、`exited` は起動の失敗とメモリ不足を、さらに呼び分ける**（「終了のわけは、確実に分かるときだけ出す」）。

**状態は、色の付いたアイコンと、状態の呼び方の文を並べて出す。** 動いているもの（動作中）は緑、動作中になる途中のもの（再起動中、起動中）は青、止めてあるもの（一時停止中）は黄（ライトの配色では橙。`design/renderer.md` の「色と背景のコントラスト」）、動いていないもの（未起動、正常終了、終了）は灰、
調べる必要があるもの（起動失敗、強制終了（メモリ不足）、削除失敗、動作中（異常））は赤にする。色とアイコンの組み合わせは、Storybook の「コンテナ/一覧」の「読み込み済み（すべての状態）」を正とする（`common.md` の「見た目の正は Storybook」）。

### 終了のわけは、確実に分かるときだけ出す

**終了コード**は、コンテナのメインのプロセスが終わるときに返した数（Docker の文書の「Running containers」の「Exit status」）。0 は成功を表す。
シグナル（プロセスに送る合図）の番号 N で終わらされたプロセスの終了コードは、128 に N を足した数になる（Bash の文書の「Exit Status」）。
英語で表示するときは、`docker ps` の `STATUS` の列と同じく、Docker の言葉に終了コードを括弧に入れて付ける（`Exited (143)`）。

**終了コードが 0 以外でも、失敗とは限らない。** ［停止］ で止めたコンテナの終了コードは、アプリの作りで変わる。
［停止］ は、`SIGTERM` を送り、待ち時間の後に `SIGKILL` を送る（Docker の文書の「docker container stop」）。
コンテナの中で最初に起動したプロセスは、受け取る処理を書いていないシグナルを無視するので、`SIGTERM` では終わらない（Docker の文書の「docker container attach」）。
「停止したときのアプリ」の表の終了コードは、開発機の Docker 29.5.2 で確かめた。

| 停止したときのアプリ | 終了コード |
| --- | --- |
| 停止の合図（`SIGTERM`）を受けたアプリが、後片付けをして自分で終わる | 0 |
| アプリが停止の合図を処理する作りになっておらず、合図を受けた OS がアプリのプロセスを終わらせる | 143（128 に `SIGTERM` の番号 15 を足した数） |
| 停止の合図を受けてもアプリが終わらず、待ち時間の後にエンジンが強制終了させる | 137（128 に `SIGKILL` の番号 9 を足した数） |
| `npm start` で動かしている | 1 |

エンジンは、誰がコンテナを止めたかを返さない。終了コードだけでは、［停止］ で止めたのか、アプリが失敗したのかを見分けられない。
**0 以外の終了コードは、正常とも異常とも呼ばず、「終了（コード 143）」と出して灰にする。**

**エンジンの記録から確実に分かる、次の 2 つだけを、赤で呼び分ける。** 2 つのどちらかに当たれば、終了コードでは呼び分けない。
`State.Error` を `State.OOMKilled` より先に見る。両方が記録にあれば、起動失敗と呼ぶ。

| エンジンの記録 | 日本語で出す言葉 | 英語で出す言葉 | 意味 |
| --- | --- | --- | --- |
| `State.Error` に文がある | 起動失敗（コード 127） | `Created (127)` か `Exited (128)`（エンジンが返す状態で選ぶ） | 起動できなかった（失敗の文の置き場所は「行の知らせ」） |
| `State.OOMKilled` が `true` | 強制終了（メモリ不足） | `OOMKilled (137)` | メモリの上限を超えたので、強制終了された |

英語で出す言葉は、Docker の言葉（`Created`、`Exited`、`OOMKilled`）に、終了コードを括弧に入れて付けたもの（`common.md` の「Docker の英語の言葉」）。
`OOMKilled` は、`docker inspect` が出すコンテナの状態の項目の名前。

**起動に失敗したコンテナの状態は、`created` か `exited` のまま変わらない。** 一度も動いていなければ `created`、前に動いていたなら `exited` のままで、`State.Error` にエンジンが返した失敗の文が入る。
起動に成功すると、`State.Error` は空に戻る。

| 起動の失敗 | 終了コード |
| --- | --- |
| 実行できない（権限が無い、ディレクトリを実行しようとした） | 126 |
| コマンドが見つからない。マウントするファイルとディレクトリの種類が合わない | 127 |
| それ以外 | 前に終了したときの終了コードが 0 なら 128。0 以外なら、前の終了コードのまま |

Engine API の文書は `State.Error` の意味と、起動に失敗したときの終了コードを書いていないので、エンジンのソースコードで確かめた（`design/main.md` の「コンテナの一覧」）。
一度も動いていないコンテナは、メモリ不足にならないので、`created` は起動の失敗だけを呼び分ける。

**why: 起動失敗を「未起動」と呼ばない。** 未起動と呼ぶと、［起動］ を押せば動くように見える。押しても、同じわけでまた失敗する。

### 動作中のコンテナは、健康状態で呼び分ける

**ヘルスチェック**は、コンテナの中のアプリが要求に応えられるかを、エンジンが決まった間隔で確かめる仕組み。
確かめ方のコマンドは、イメージ、Compose のファイル、`docker run` の `--health-cmd` のどれかで指定する。ヘルスチェックを書いたコンテナだけが、確かめた結果（**健康状態**）を持つ。

**エンジンは、コンテナの中のプロセスが動き始めた時点で `running` を返す。** データベースのように、要求に応えられるようになるまで時間がかかるアプリでは、
`running` を見ただけでは、使えるようになったかが分からない。**動作中のコンテナは、健康状態で呼び分ける。**

| 健康状態 | 日本語で出す言葉 | 英語で出す言葉 | 意味 |
| --- | --- | --- | --- |
| `starting` | 起動中 | `Starting` | 確かめが、まだ 1 回も成功していない |
| `healthy` | 動作中 | `Running` | 確かめが成功している |
| `unhealthy` | 動作中（異常） | `Running (unhealthy)` | 確かめが、決まった回数続けて失敗した |
| 無し（ヘルスチェックを書いていない） | 動作中 | `Running` | — |

動作中（異常）は、コンテナの中のプロセスは動いているが、アプリが要求に応えていない状態。ログを読む必要があるので、赤にする（「状態の呼び方」の色）。

**起動中と動作中（異常）は、状態の列の呼び方・色・アイコンのほかは、動作中と同じに扱う。** 並び順、絞り込み、時間の列、押せるボタンは、動作中と同じ。
コンテナの中のプロセスは動いているので、停止も再起動もできる。

**why: 健康状態を別の列にしない。** 健康状態を持つのは動作中のコンテナだけで、ほかの行では列が空になる。

### `dead` はコンテナの終了ではない

**`dead` は、エンジンがコンテナの削除を始めて、完了できずに残っている状態。**
コンテナのプロセスの終了（`exited`）とは別のもので、混同すると原因の調べ先を間違える。

`dead` のコンテナは、DockerGUI からは起動も停止も削除もできない。
詳細の画面に、**エンジンを起動し直すと削除できることが多い**と案内を出す。

### 並び順

動作中・一時停止中・再起動中のコンテナを、まとめて**「起動しているコンテナ」**と呼ぶ。

**起動しているコンテナを先に出し、ほかのコンテナを後に出す。** それぞれの中では、名前の順に並べる。

**why: 一覧を開く目的の多くは、いま起動しているコンテナを見ることにある。**
終了したコンテナが上に並ぶと、目的のコンテナを探すことになる。

**why: 一時停止中と再起動中のコンテナも、先に出す。** 一時停止中のコンテナは、メモリの中身を残したまま止まっていて、［再開］ ですぐに続きから動く（「一時停止と停止の違い」）。
再起動中のコンテナは、エンジンが再起動の方針に従って起動し直している途中のコンテナ（「状態の呼び方」）。
エンジンも、一時停止中と再起動中のコンテナの `Running` を true にする（moby の `daemon/container/state.go`。`master` の `43fbbcb58fd3`、2026-10-01 に読んだ）。

### 絞り込み

名前とイメージの名前の両方を対象に、入力した文字を含むコンテナだけを出す。

あわせて、**終了したコンテナを隠す切り替えを置く。** 既定は隠さない。
隠すのは、正常終了と終了（コード 143 など）のコンテナだけ。どちらも、終了のわけが分からない終了で、灰色で出す（「終了のわけは、確実に分かるときだけ出す」）。

一覧の上に、絞り込みの入力と、切り替えを並べる。

| 部品 | 出す文 |
| --- | --- |
| 絞り込みの入力 | 入力の中の薄い文 `名前かイメージで絞り込む` |
| 切り替え | チェックボックスと `終了したコンテナを隠す` |

**絞り込みに当てはまるコンテナが無いときは、一覧の代わりに `絞り込みに当てはまるコンテナがありません` を出す。**
絞り込みの入力と切り替えは、出したままにする。「1 件も無いとき」の文を出すと、コンテナがあるのに無いと読める。

**切り替えは、アプリを開き直しても元のままにする**（`settings.md` の「設定の画面に出すもの」）。絞り込みの入力は覚えない。

**why: 終了したコンテナは溜まる。** 一覧が終了したコンテナで埋まると、
起動しているコンテナが画面に収まらなくなる。

| 隠さないコンテナ | why |
| --- | --- |
| 未起動 | 作ってから、まだ一度も起動していない。起動するために作ったコンテナなので、隠すと、起動したいコンテナを探すことになる |
| 起動失敗、強制終了（メモリ不足）、削除失敗 | 赤で出す、利用者が調べる必要のあるコンテナ（「状態の呼び方」）。隠すと、失敗に気づかない |
| 削除中 | 削除が終われば、一覧から消える |

### 1 件も無いとき

```
コンテナが 1 件もありません
Compose の画面からプロジェクトを起動すると、コンテナが増えます
```

## 詳細

**詳細は、一覧の列に出ない値を読むために開く。** 起動に失敗したわけ、実行しているコマンド、マウント、ネットワークの IP アドレスなど。

行の右端の ［詳細］ を押すと、コンテナの詳細を、一覧の右から重ねて出す。この形を**重ねた詳細**と呼ぶ。
**重ねた詳細を出している間も、一覧の左側（状態と名前の列）は見えたままにする。** 一覧の右側は詳細に隠れる。見えている左側は暗くなる。
見出しの ［閉じる］ は、画面では × の絵のアイコンで出す（図の中の ［閉じる］ は、配置だけを表す）。

```
┌────────────┬────────────────────┐
│ ● 動作中    web-1     │ web-1          ［拡大］ ［閉じる］     │
│ ○ 正常終了  db-1      │ コンテナ ID   1bf72c7aee3e…           │
│                        │ 名前          web-1                    │
│                        │ イメージ      nginx:1.27               │
└────────────┴────────────────────┘
```

**［拡大］ は、詳細の値が重ねた詳細の幅では読みにくいときに使う。** 長いパスやラベルが何行にも折り返されるときなど。
重ねた詳細の見出しの ［拡大］ を押すと、詳細を一覧と入れ替えて、右の領域（`common.md` の「画面の構成」の「一覧と詳細」）いっぱいに出す。この形を**広げた詳細**と呼ぶ。
広げた詳細の見出しの ［縮小］ を押すと、重ねた詳細に戻る。

```
┌────────┬────────────────────────┐
│ コンテナ       │ web-1                  ［縮小］ ［閉じる］     │
│ イメージ       │ コンテナ ID   1bf72c7aee3ed68c6b48d6b8…       │
│ ボリューム     │ 名前          web-1                            │
│ ネットワーク   │ イメージ      nginx:1.27                       │
└────────┴────────────────────────┘
```

| 形 | 出す場所 | 見出しのボタン | どうやってその形になるか |
| --- | --- | --- | --- |
| 重ねた詳細 | 一覧の右から重ねる | ［拡大］［閉じる］ | 行の ［詳細］ を押した。広げた詳細で ［縮小］ を押した |
| 広げた詳細 | 一覧と入れ替えて、右の領域いっぱい | ［縮小］［閉じる］ | 重ねた詳細で ［拡大］ を押した |

**詳細は、いつも重ねた詳細の形で開く。** 前に開いた詳細を広げていても、次に開くときは重ねた詳細にする。
**why: 広げた詳細で開くと、一覧が隠れたままになる。** どのコンテナの詳細を開いたかを、一覧と見比べて確かめられない。

**広げた詳細を出している間は、状態バーと左の一覧を操作できる。** 広げた詳細は、一覧の代わりに右の領域に出るだけで、画面の上に重ならない。
**左の一覧で別の対象を選ぶと、詳細を閉じる。** 左の一覧で別の対象を選ぶと、コンテナの画面の状態を捨てる（`design/renderer.md` の「右の領域: 開いているタブの screen は、閉じるまで動かし続ける」）。コンテナに戻ると、一覧を出す。

| 状態 | 表示する内容 | ボタン |
| --- | --- | --- |
| 読み込み中 | 見出しにコンテナの名前。本文にスケルトン | 見出しのボタン（形の表） |
| 読み込み済み | 見出しにコンテナの名前。本文に項目の表 | 見出しのボタン（形の表） |
| 取得失敗 | 見出しにコンテナの名前。本文に失敗の文（`common.md` の「失敗の見せ方」） | ［もう一度読み込む］と、見出しのボタン（形の表） |

| 状態 | どうやってその状態になるか |
| --- | --- |
| 読み込み中 | 行の ［詳細］ を押した。「取得失敗」で ［もう一度読み込む］ を押した |
| 読み込み済み | 読み込みが終わった |
| 取得失敗 | 読み込みが失敗した（コンテナが削除されていた、エンジンに繋がらなかった、など） |

失敗の文の例: `コンテナ web-1 の詳細を読み込めませんでした。<原因>`

**詳細は、どちらの形でも、［閉じる］ を押すか、`Esc` を押すと閉じる**（`common.md` の「キーボードの操作」）。重ねた詳細は、詳細の外の暗くなった部分を押しても閉じる。広げた詳細を閉じると、DockerGUI は詳細の代わりに一覧を出す。
**広げた詳細の `Esc` は、フォーカスが広げた詳細の中にあるときと、どの部品にも無いときだけ、詳細を閉じる。** 状態バーのメニューを開いているときの `Esc` は、メニューだけを閉じる。
**why: 1 回の `Esc` で 1 つだけ閉じる。** メニューを閉じたつもりで詳細まで閉じると、開き直すことになる。重ねた詳細は画面の上に重なるので、重ねた詳細を出している間は、メニューを開けない。
**エンジンとの接続が切れたときも、詳細を閉じる。** 接続し直した後のエンジンに、同じコンテナがあるとは限らない。

**重ねた詳細を出している間は、一覧を操作できない。** 一覧の右側の行のボタンは、詳細に隠れる。
別のコンテナの詳細を見るときは、詳細の外を押して閉じてから、別の行の ［詳細］ を押す。

**詳細は、開いたときに読んだ値を出す。** 開いている間にコンテナの状態が変わっても、読み直さない。読み直すには、閉じてから開き直す。

| 項目 | 内容 |
| --- | --- |
| コンテナ ID | 全体を出す（`common.md` の「利用者がコピーして使いたい値」） |
| 名前 | コンテナの名前 |
| イメージ | イメージの名前とタグ。その下に、イメージ ID の全体 |
| 状態 | 状態の呼び方とアイコン（「状態の呼び方」）。起動または削除に失敗した場合は、その下に、エンジンが返した失敗の文（`State.Error`）も出す。文は訳さない（`common.md` の「訳さないもの」） |
| コマンド | 実行するファイルと引数を、空白で区切って並べる。空白や記号を含む引数は `'` で囲む |
| 作成した日時 | `common.md` の「表記」の「詳細とログの時刻」 |
| 起動した日時 | 作成した日時と同じ形。まだ起動していない場合は空 |
| ポート | 外に公開しているポートの対応を、1 行に 1 つ、`8080 → 80/tcp` の形で出す。IPv4 と IPv6 の同じ公開は 1 つにまとめる（「出す列」のポートと同じ） |
| マウント | 1 行に 1 つ、`マウント元 → コンテナの中のパス` の形で出す。マウント元は、ボリュームならボリュームの名前、ホストのパスならホストのパス。マウント元の無い `tmpfs` は、マウント元の代わりに `tmpfs` と出す。コンテナの中のパスの順に並べる |
| ネットワーク | つながっているネットワークの名前と IP アドレス。**ネットワークごとに 1 行ずつ出す**。IP アドレスの無いネットワークは、名前だけを出す |
| 再起動の設定 | `no` `always` `unless-stopped` `on-failure` のどれか。`on-failure` では、再試行の回数の上限も出す（`on-failure（最大 3 回）`）。上限が 0 なら、上限が無いことを出す（`on-failure（回数の上限なし）`） |
| 環境変数 | コンテナを作るときに指定した環境変数（`docker run -e`、Compose の `environment` など）。名前と値の両方がイメージの環境変数と同じものを除く。値を伏せて出し、［表示］ を置く（「環境変数は既定で隠す」を参照） |
| イメージの環境変数 | イメージを作るときに決めた環境変数（Dockerfile の `ENV`）のうち、コンテナを作るときに同じ名前で別の値を指定していないもの。1 行に 1 つ、名前と値を伏せずに出す。エンジンが返した順のまま並べる |
| ラベル | 1 行に 1 つ、キーと値。キーの順に並べる |

**値が 1 つも無い項目（公開していないポート、マウントの無いコンテナなど）は、空にする。** 項目の名前は出したままにする。

**コピーのアイコンは、コンテナ ID、名前、イメージの名前とタグ、イメージ ID、マウント元のボリュームの名前、ネットワークの名前、IP アドレスの右に置く**（`common.md` の「利用者がコピーして使いたい値」）。
IP アドレスの無いネットワークには、IP アドレスのコピーのアイコンを置かない。ボリューム以外のマウント元（ホストのパス、`tmpfs`）と、ほかの項目には置かない。
マウスを重ねると、何をコピーするかを出す（`コンテナ ID をコピー`、`ネットワーク shop_default の IP アドレスをコピー` など）。

**why: コマンドの引数を `'` で囲む。** 空白を含む引数（`daemon off;`）を空白で区切ってつなぐと、引数の区切りが読めなくなる。
シェルと同じ囲み方にすると、ターミナルに貼り付けて同じ引数で実行できる。

**why: ポートにプロトコルも出す。** 同じ番号を `tcp` と `udp` の両方で公開していると、プロトコルが無いと同じ行が 2 つ並ぶ。
一覧のポートの列は狭いので、一覧にはプロトコルを出さない。

**why: 再起動の回数の上限が 0 のときに、上限が無いことを出す。** エンジンは、上限が 0 なら回数を数えずに再起動を続ける
（Docker の文書の「docker container run」の「Restart policies」、moby（docker-v29.5.2）の `daemon/internal/restartmanager/restartmanager.go` の `ShouldRestart`）。
`docker run --restart on-failure` のように回数を書かずに作ると、上限は 0 になる。0 をそのまま出すと、再起動しないと読める。

### 環境変数は既定で隠す

コンテナの環境変数には、コンテナを作るときに指定した環境変数と、イメージ（`overview.md` の「イメージとコンテナは別のもの」）を作るときに決めた環境変数の 2 つが入る。
**伏せるのは、コンテナを作るときに指定した環境変数だけ。** イメージの環境変数は、「イメージの環境変数」の項目に、伏せずに出す。
名前と値の両方がイメージの環境変数と同じものは、作るときに指定していても、イメージの環境変数として出す（`design/main.md` の「コンテナの詳細」の、環境変数の出どころの行）。
**イメージを読めないとき（イメージを削除したときなど）は、「イメージの環境変数」を空にし、すべての環境変数を「環境変数」の項目に伏せて出す。** どの環境変数がイメージのものか分からないので、値を伏せるほうにする。

**why: イメージの環境変数は伏せない。** イメージの環境変数の値は、イメージを持っている人なら誰でも読める（`docker image inspect`）。
伏せると、`NODE_VERSION` のような秘密でない値まで、1 つずつ ［表示］ を押して読むことになる。

「環境変数」の項目では、作るときに指定した環境変数ごとに、値を伏せて出し、［表示］ を置く。［表示］ を押すと、押した行の環境変数の値を出し、ボタンを ［隠す］ に変える。
［隠す］ を押すと、値をまた伏せる。作るときに指定した環境変数は、エンジンが返した順のまま並べる。
画面を読み上げる機能には、ボタンの名前として、作るときに指定した環境変数の名前を入れて渡す（`DB_PASSWORD の値を表示`、`DB_PASSWORD の値を隠す`）。

```
DATABASE_URL   ●●●●●●●●                         ［表示］
NGINX_PORT     80                               ［隠す］
```

| 状態 | 表示する内容 | ボタン |
| --- | --- | --- |
| 非表示 | 作るときに指定した環境変数の名前と `●●●●●●●●` | ［表示］ |
| 表示中 | 作るときに指定した環境変数の名前と値 | ［隠す］ |

| 状態 | どうやってその状態になるか |
| --- | --- |
| 非表示 | 詳細を開いた。［隠す］ を押した |
| 表示中 | ［表示］ を押した |

**why: 作るときに指定した環境変数には、パスワードと API のキーが入っていることが多い。**
画面を共有しながら作業することと、画面を録画することがあるため、
利用者が開く操作をするまで値を出さない。

**伏せた値は、値の長さによらず `●` を 8 つ並べる。** 値が空でも同じにする。
**why: 伏せた値の長さから、値を推し量れないようにする。** 値の長さが分かると、短い暗証番号や、値が空であることが分かる。

**詳細を開き直すと、作るときに指定した環境変数の値を、すべて伏せる。** ［拡大］ と ［縮小］ では、出している値をそのままにする。
**why: 値を出したまま詳細を閉じても、次に詳細を開いたときには、作るときに指定した環境変数の値が、すべて伏せてある。** そのため、詳細を閉じた後で画面を共有しても、前に出した値は見えない。

## 操作

| 操作 | 押すボタン | 出す状態 | 確認 |
| --- | --- | --- | --- |
| 起動 | ［起動］ | 未起動、起動失敗、正常終了、終了、強制終了（メモリ不足） | 無し |
| 一時停止 | ［一時停止］ | 動作中 | 無し |
| 再開 | ［再開］ | 一時停止中 | 無し |
| 停止 | ［停止］ | 動作中、一時停止中 | 無し |
| 強制停止 | ［強制停止］ | **停止処理中だけ**（「停止は待たされる」を参照） | 無し |
| 再起動 | ［再起動］ | 動作中 | 無し |
| 削除 | ［削除］ | 削除失敗（`dead`）以外のすべての状態 | **有り** |

**出す状態に当てはまらないボタンは、出さない**（`common.md` の「その状態で使えないボタンは、出さない」）。

**行のボタンは、行の右端にアイコンで並べる。** マウスを重ねると、ボタンの名前を出す。
アイコンには色を付ける。起動と再開は緑、一時停止は黄、再起動は青で、操作の後の状態（動作中、一時停止中、再起動中）と同じ色にする。停止は、コンテナの中のプロセスを終わらせるので赤にする。削除は、元に戻せないので赤にする。
色とアイコンの組み合わせは、Storybook の「コンテナ/一覧」の「読み込み済み（すべての状態）」を正とする。
行の右端には、状態ごとの操作のボタンに加えて、［詳細］（「詳細」）と、ログとターミナルのボタンも並ぶ（「ログとターミナルを開く」）。文字のボタンにすると、一覧の幅の多くをボタンが使う。

**［詳細］ は、すべての状態で、行の右端に出す。** 停止処理中も出す。詳細は、コンテナの状態によらず読めるため。

```
● 動作中    web-1   nginx:1.27   8080 → 80   3 分前      ［一時停止］［停止］［再起動］［削除］
○ 正常終了  db-1    postgres:16               1 時間前                            ［起動］［削除］
```

停止処理中（「停止は待たされる」で定義する）の知らせと、操作の失敗の知らせを、まとめて**「行の知らせ」**と呼ぶ。
**行の知らせは、コンテナの行の 2 段目に、字下げして出す**（操作の失敗は `common.md` の「失敗の置き場所」の「操作した対象の行」）。
1 段目と 2 段目の間に線を引かず、マウスを重ねたときの色も 2 段をまとめて変え、1 つの行に見せる。

**why: 別の行に見せない。** 別の行に見えると、知らせがどのコンテナのものかを、上の行を見て確かめることになる。

| 行の知らせ | 出している間 | ボタン |
| --- | --- | --- |
| 停止処理中の知らせ | 停止処理中の間（「停止は待たされる」） | ［強制停止］ |
| 操作の失敗の知らせ | 操作が失敗してから、［閉じる］ を押すまで。同じコンテナで操作をやり直したとき、コンテナが一覧から消えたとき、エンジンとの接続が切れたときも消す | ［閉じる］。原因の文が 1 行に収まらないときは ［全文を表示］ か ［たたむ］ も |

```
● 動作中    web-1   nginx:1.27   8080 → 80   3 分前      ［一時停止］［停止］［再起動］［削除］
  ! コンテナ web-1 を停止できませんでした。<エンジンが返した文>                        ［閉じる］
```

**操作の失敗の知らせは、1 行に収める。** 原因の文が 1 行に収まらないときは、原因の文の先頭を「…」にして末尾を残し、［全文を表示］ を置く。
［全文を表示］ を押すと、知らせを折り返して全文を出し、ボタンを ［たたむ］ に変える。何ができなかったか（「コンテナ web-1 を起動できませんでした。」）は、切り詰めない。

```
○ 未起動    web-1   nginx:1.27                                            ［起動］［削除］
  ! コンテナ web-1 を起動できませんでした。…18996 failed: port is already allocated  ［全文を表示］［閉じる］
```

**why: 原因の文の先頭ではなく、末尾を残す。** エンジンが返す起動の失敗の文は、1 行に収まらないことが多い（開発機で、コマンドが無い場合とポートが使われている場合を確認）。
文の前半はエンジンの内部の段階の名前で、原因（`port is already allocated` など）は末尾にある。
画面に描いた幅で切るので、エンジンの文の形を読まずに済む（`design/main.md` の「コンテナの一覧」の、`Status` の英語の文を読まない決めごと）。

**why: 1 行に収める。** 折り返すと、行の高さが知らせの文の長さでばらつき、一覧が読みにくくなる。

**起動の失敗の文（`State.Error`）は、一覧に出さず、詳細の画面に出す**（「詳細」）。一覧では、赤の「起動失敗（コード 127）」で、調べる必要があることを知らせる。

**why: 起動の失敗の文は、詳細の画面で読む。** 起動の失敗の原因の多くは、コンテナの設定（コマンド、ポート、マウント）にある。詳細の画面なら、失敗の文と設定を並べて読める。
`State.Error` は次に起動に成功するまで残るので、一覧に出すと、起動に失敗したコンテナの行が 2 段のままになる。
DockerGUI で ［起動］ を押して失敗したときは、操作の失敗の知らせに、`State.Error` と同じ文が出る（エンジンは、起動の失敗を `State.Error` に記録し、同じ失敗を応答として返す。`design/main.md` の「コンテナの一覧」）。

**why: 接続が切れたら、操作の失敗の知らせを消す。** 操作の失敗は、接続が切れる前のエンジンのコンテナについてのもので、接続し直した後の一覧には当てはまらない。

操作の共通の約束（実行中は同じ操作を受け付けない、成功は知らせない、失敗は画面に残す）は
`common.md` に書いてある。

### 一時停止と停止の違い

**一時停止は、メモリの中身を残したまま、CPU だけを空ける操作。**

| | 停止 | 一時停止 |
| --- | --- | --- |
| コンテナの中のプロセス | 終了する | 止まったまま残る |
| メモリの中身 | 消える | 残る |
| CPU | 空く | 空く |
| 動かし直すとき | ［起動］。コンテナの中のアプリの起動を待つ | ［再開］。止めた所からすぐ続く |

**一時停止を使う場面は、動かし直すまでの時間を短くしたいとき。** たとえば、データを読み込むのに
数分かかるコンテナを、別の重い作業の間だけ止めておく場合。停止すると、再開のときに
データの読み込みからやり直しになる。

**一時停止してもメモリは空かない。** メモリを空けたいときは停止する。
［一時停止］ と ［停止］ を並べて出すので、詳細の画面に、一時停止ではメモリが空かないことを添える。

**確認は出さない。** 一時停止も再開も、取り返しのつかない操作ではない。

**DockerGUI の外で一時停止されたコンテナも、［再開］ で動かせる。**

### 停止は待たされる

停止の要求を受けたエンジンは、コンテナに `SIGTERM` を送り、
待ってから `SIGKILL` で強制的に終了させる。
**待ち時間の既定はエンジンが決めていて、Linux のコンテナでは 10 秒。**

停止の完了を待っている間の行の状態を**「停止処理中」**と呼ぶ。次の間も、停止処理中にする。

- 動作中と一時停止中のコンテナの削除で、削除の前の停止を待っている間（「削除の確認」）
- 再起動の応答を待っている間（「再起動は、停止してから起動する」）

**停止処理中は、行の右端のボタンを消し、行の 2 段目に、行の知らせとして次の文を出す**。並びは `common.md` の「待たせるときの表示」に従う。

```
● 動作中    web-1   nginx:1.27   8080 → 80   3 分前
  web-1 を停止しています…  経過 00:04  ［強制停止］
```

**why: 行の右端に出さない。** 停止処理中の文は、ボタンより長い。行の右端に出すと、列が広がり、ほかの列が横に動く。

**停止処理中だけ ［強制停止］ を出す。** 押すと待ち時間を 0 にして、
エンジンがコンテナを即座に強制終了する。

**中止のボタンは置かない。** エンジンはコンテナに `SIGTERM` を送った時点で停止を始めていて、
送った合図を取り消す手段が無い（`common.md` の「待たせるときの表示」の例外）。
待てない利用者のために、代わりに ［強制停止］ を置く。

**why: 終了の合図を無視するコンテナがある。** 10 秒待つと分かっていても、
待てない場面がある。逆に、待てば正常に終了するコンテナを毎回強制終了させると、
書き込みの途中でデータが壊れる。**既定は待ち、利用者が選んだときだけ強制終了する。**

### 再起動は、停止してから起動する

**エンジンは、［再起動］ を受けると、停止してから起動する**（moby の `daemon/restart.go`。`master` の `43fbbcb58fd3`、2026-10-01 に読んだ）。
前半の停止は、［停止］ と同じく待たされる（「停止は待たされる」）。後半の起動は、［起動］ と同じ。

**状態の列は、再起動の途中も、エンジンの状態に従う。** 再起動中にはならない（「状態の呼び方」）。
**行の 2 段目には、再起動の応答が届くまで、停止処理中の知らせを出す。**

| 再起動の途中 | 状態の列 | 行の 2 段目 | ボタン |
| --- | --- | --- | --- |
| 前半の停止 | 動作中 | 停止処理中の知らせ | ［強制停止］ |
| 停止が終わってから、起動が始まるまで | 正常終了か、終了（コード N）になることがある | 停止処理中の知らせ | ［強制停止］（押しても何も起きない） |
| 後半の起動 | ［起動］ と同じく、エンジンの状態に従う。ヘルスチェックのあるコンテナは、起動中を挟んで動作中になる（「動作中のコンテナは、健康状態で呼び分ける」） | 停止処理中の知らせ | ［強制停止］ |

エンジンは、コンテナの停止が終わると、状態を `exited` にする（`daemon/monitor.go` の `handleContainerExit`）。起動は、停止が終わってから始める（`daemon/restart.go`）。

**why: 再起動の途中で、行のボタンを出したり消したりしない。** 停止が終わってから起動が始まるまでの間に、状態に合わせて ［起動］ などのボタンを出すと、一瞬だけボタンが出て、押し間違える。

**前半の停止の間に ［強制停止］ を押すと、コンテナはすぐに強制終了され、再起動は起動に進む。** コンテナは止まったままにならない。
エンジンの再起動は、強制終了でもコンテナの停止が終われば、起動に進む（`daemon/restart.go`）。開発機でも、再起動の途中に強制停止を送り、コンテナが起動し直したことを確かめた。

**停止が終わってから起動が始まるまでの間に ［強制停止］ を押しても、何も起きない。** DockerGUI は、強制停止を動作中と一時停止中のコンテナにだけ送る（`design/main.md` の「コンテナの操作」）。

**起動が終わってから応答が届くまでの短い間に ［強制停止］ を押すと、起動し直したコンテナが強制終了されることがある。** この間のコンテナは動作中なので、DockerGUI は強制停止を送る。
画面は、再起動の応答が届くまで、起動が終わったことを知らない。この間は短い（開発機では、エンジンの起動の出来事から、画面に応答が届くまで、0.1 秒に満たなかった）。

### 削除の確認

［削除］ を押すと、削除する前に確認の画面を出す（`common.md` の「取り返しのつかない操作は、確認を挟む」）。

```
┌────────────────────────┐
│ コンテナ web-1 を削除します。                  │
│ 元に戻せません。                               │
│                                                │
│                      [ やめる ]  [ 削除する ]  │
└────────────────────────┘
```

**動作中・一時停止中・再起動中のコンテナを削除する場合は、停止も行うことを確認の画面に表示する。**

```
┌─────────────────────────┐
│ コンテナ web-1 を削除します。                    │
│ web-1 は動作中なので、停止してから削除します。   │
│ 元に戻せません。                                 │
│                                                  │
│                      [ やめる ]  [ 削除する ]    │
└─────────────────────────┘
```

**why: 動作中・一時停止中・再起動中のコンテナの削除は、停止を伴う。**
停止することを書かないと、利用者はコンテナが止まると考えずに削除する。

日本語の文では、停止する理由に、行の状態の列と同じ呼び方を入れる（「web-1 は一時停止中なので、」「web-1 は起動中なので、」）。
英語の文では、Docker の言葉を小文字のまま入れる（「web-1 is running, so」）。

**why: 英語では、状態の列の呼び方を文に入れない。** 英語の状態の列は、Docker の言葉の先頭を大文字にした名前（`Running (unhealthy)`）で、文の途中に入れると読みにくい。

**削除するコンテナが 2 つ以上のときは、件数と、名前を 1 行に 1 つずつ並べる**（`common.md` の「取り返しのつかない操作は、確認を挟む」）。
停止してから削除するコンテナには、名前の後に理由を添える。日本語の文では、行の状態の列と同じ呼び方を入れ、英語の文では、Docker の言葉を小文字のまま入れる（「web-1 (running, so …)」）。
選択の帯から削除しても、削除できる状態のコンテナが 1 つだけなら、1 つのときの文にする。確認の画面を開いている間に 1 つに減ったときも、1 つのときの文に変える。

```
┌─────────────────────────────┐
│ コンテナ 3 件を削除します。                              │
│ web-1（動作中なので、停止してから削除します）            │
│ db-1（一時停止中なので、停止してから削除します）         │
│ job-1                                                    │
│ 元に戻せません。                                         │
│                                                          │
│                                [ やめる ]  [ 削除する ]  │
└─────────────────────────────┘
```

**why: 名前ごとに、停止するかを書く。** 件数だけを書くと、どのコンテナが止まるかを、利用者が一覧に戻って確かめることになる。

| 場面 | 確認の画面 |
| --- | --- |
| ［削除する］ を押した | 閉じて、削除を始める |
| ［やめる］ を押した。Esc を押した。確認の画面の外を押した | 閉じる。削除しない |
| 確認の画面を開いている間に、削除するコンテナが一覧から消えた | 消えたコンテナを、確認の画面から外す。1 つも残らなければ、削除するコンテナがもう無いので閉じる |
| 確認の画面を開いている間に、一覧を読み込めなくなった | 閉じる。一覧の場所が失敗の表示に変わり、削除するコンテナが今もあるかを確かめられない |
| エンジンとの接続が切れた | 閉じる。一覧と一緒に消える（`common.md` の「一覧の状態」） |

確認の画面には見出しを付けないので、画面を読み上げる機能には、確認の画面の名前として「コンテナの削除の確認」（英語では「Confirm removal」）を渡す。削除するコンテナの数によらず、同じ名前にする（`common.md` の「取り返しのつかない操作は、確認を挟む」）。

削除の前の停止を待つ間の行は、「停止は待たされる」の停止処理中になる。停止処理中に ［強制停止］ を押すと、すぐに停止して、削除に進む。
**再起動中のコンテナは、削除の応答を待っている間も、停止処理中にしない。** 行の ［削除］ を押せない状態にする（`common.md` の「実行中は、同じ操作を受け付けない」）。

**why: 再起動中のコンテナに ［強制停止］ を出しても、何も起きない。** DockerGUI は、強制停止を動作中と一時停止中のコンテナにだけ送る（`design/main.md` の「コンテナの操作」）。

### まとめて操作する

一覧で複数のコンテナを選び、起動・一時停止・再開・停止・再起動・削除をまとめて実行できる。

**行の左端のチェックボックスで、コンテナを選ぶ。** チェックボックスで選んだコンテナを**「選択したコンテナ」**と呼ぶ。
見出しの行の左端には、一覧に出ている行をまとめて選ぶチェックボックスを置く。

| 一覧に出ている行の選択 | 見出しのチェックボックスの表示 | 押したとき |
| --- | --- | --- |
| 一覧に出ている行を、1 つも選択していない | 無し | 一覧に出ている行を、すべて選択する |
| 一覧に出ている行の、一部を選択している | 横線 | 選択を、すべて外す |
| 一覧に出ている行を、すべて選択している | チェック | 選択を、すべて外す |

**why: 一部を選択しているときに押すと、すべて外す。** 選択を外すボタンを置かずに、見出しのチェックボックスを 1 回押すだけで、選択をすべて外せる。

絞り込みの入力の下に出す、まとめて操作するボタンを並べた帯を、**「選択の帯」**と呼ぶ。
**1 件以上選択している間だけ、選択の帯を出す。**

```
（絞り込みの入力）  [ ] 終了したコンテナを隠す
［起動］［一時停止］［停止］［再起動］［削除］
```

- **選択の帯の操作のボタンは、選択したコンテナのうち 1 件でも操作できる状態のものだけを出す**（`common.md` の「その状態で使えないボタンは、出さない」）。出すボタンが 1 つも無いときは、選択の帯を出さない。
- **ボタンは、行の操作のボタンと同じアイコンと色に、操作の名前を並べる。** 並び順は、起動・一時停止・再開・停止・再起動・削除。
- **選択したコンテナのうち 1 件でも、その操作の応答を待っている間は、選択の帯のそのボタンを押せない状態にする**（`common.md` の「実行中は、同じ操作を受け付けない」）。
- **まとめて操作したときの停止処理中の知らせと、操作の失敗の知らせは、コンテナの行ごとに出す**（「行の知らせ」）。

**why: 選択の帯のボタンには、名前も出す。** 行のボタンは、マウスを重ねないと名前が出ない。まとめて操作すると、いくつものコンテナが一度に変わるので、選択の帯のボタンは、押す前に何をするかを読めるように、名前も出す。

| 選択が外れる場面 | why |
| --- | --- |
| 行のチェックボックスを押した。見出しのチェックボックスで、すべて外した | 利用者が外した |
| 選択したコンテナが、一覧から消えた | `common.md` の「自動で更新する」（選んでいる行が消えた場合だけ、選択を外す） |
| 選択したコンテナが、絞り込みで隠れた | 見えていないコンテナを、気づかずに操作しないため。絞り込みを戻しても、選択は戻らない |
| エンジンとの接続が切れた | 選択が、一覧と一緒に消える（`common.md` の「一覧の状態」） |

**まとめて操作した後も、選択したままにする。**

**why: 同じコンテナで、続けて操作できる。** 停止してから削除するように、同じコンテナに続けて操作することが多い。削除したコンテナは一覧から消えるので、選択からも外れる。

- **選んだコンテナのうち、操作できる状態のものだけを実行の対象にする。**
  動作中のコンテナと終了したコンテナを選んで［起動］を押した場合、
  終了したコンテナだけを起動する。
- **削除の確認の画面の文は、「削除の確認」のとおり。**
- **一部が失敗しても、残りは実行する。** 失敗したコンテナの行に、操作の失敗の知らせを出す（「行の知らせ」）。

**why: まとめて操作する場面では、対象が多い。**
1 件の失敗で全部が止まると、どこまで実行されたのかを利用者が確かめることになる。

## ログとターミナルを開く

一覧の行から、ログの画面とターミナルの画面を開く。

| 開くもの | 開ける状態 | 仕様 |
| --- | --- | --- |
| ログ | すべての状態 | `logs.md` |
| ターミナル | 動作中 | `terminal.md` |

**終了したコンテナのログは読める。** コンテナが終了していても、エンジンはログを保持している。
**why: 利用者がログを読みたい場面の多くは、コンテナが終了した後にある。**

**ターミナルは動作中のコンテナでしか開けない。** 動作中でないコンテナには、
コマンドを実行する相手がいない。動作中でないコンテナには、ターミナルを開くボタンを出さない
（`common.md` の「その状態で使えないボタンは、出さない」）。

## 一覧の更新

コンテナの状態が変わった時点で一覧を更新する。一定の間隔で取り直すことはしない（設計方針の原則 5）。

更新の対象は、コンテナの作成・起動・停止・強制終了・削除、および健康状態の変化。
