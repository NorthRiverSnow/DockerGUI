# DockerGUI

Docker を画面から操作するデスクトップアプリ。コンテナの起動・停止・ログ確認といった、
毎日繰り返す操作をターミナルに打ち込まずに済ませる。macOS と、Windows の WSL 環境で動かす。

## 言語

やり取り・コミットメッセージ・ドキュメントはすべて日本語。

## 利用者

利用者は、デスクトップアプリの開発と Docker の経験が少ない。

- 新しい用語は、使う前に 1 文で説明する
- 質問に答えた説明は、頼まれない限り docs に追加しない
- 利用者は WSL の環境を持っていない。WSL でしか確かめられないことは、確かめられないと書く

| `docs/design/layers.md` | 設計。層の分け方。設計の docs の一覧もここにある |
| `docs/spec/common.md` | 全画面に共通する約束 |
| `docs/spec/connection.md` | 接続と診断 |
| `docs/spec/containers.md` | コンテナ |
| `docs/spec/logs.md` | ログ |
| `docs/spec/terminal.md` | ターミナル |
| `docs/spec/images.md` | イメージ |
| `docs/spec/volumes-networks.md` | ボリュームとネットワーク |
| `docs/spec/compose.md` | Compose |

- 仕様を書くときは Skill の `spec-writing` を読む
- 設計を変えるときは docs も直す。実装と docs が食い違ったら docs が正
- docs は現行仕様だけを書く。履歴（「以前は X だった」）は git log の役目

## 日本語の書き方

コメント・テスト名・docs・チャットのすべてに適用する。例と詳しい規則は Skill の `writing-ja`。

1. 主語が前の文と変わるときは、主語を書く。目的語は省略しない
2. 多義語を使わない（落とす、効く、上げる、流す）
3. **指示語と代名詞を使わない。** 名前で呼ぶ。表や節も、位置ではなく名前で呼ぶ
4. 独自の呼び方は、使う前に定義する
5. 外来語はカタカナで書く。英単語を日本語の文に混ぜない
6. 状況の説明で終わらせず、因果を書く
7. 経緯を書かない

### DockerGUI で決まっている言葉

| 使わない | 使う | 使う場面 |
| --- | --- | --- |
| この道具 | DockerGUI、アプリ | 作っているもの自体を指すとき |
| 印 | アイコン | 画面に出す絵 |
| 端末 | ターミナル、コンソール | すべて |
| 選ぶ | 選択する | 画面に表示する文 |
| 足す | 追加する | 画面に表示する文 |
| 書く | 表示する | 画面に文を表示することを説明するとき |

仕様の説明の文では「選ぶ」「足す」を使ってよい。画面に表示する文と区別する方法は、
`spec-writing` の「画面に出す文と、仕様の中の名前を分ける」。

## コードを書く

- コマンドは `vp` に統一する。`npm` `npx` などを直接実行しない。テストは `vp test`、検査は `vp check`。
  一覧は `design-policy.md` の「開発で使うコマンド」
- コードの書き方（関数で書く、クラスの使いどころ、MVC の分け方）は `design-policy.md` の「守る原則 — コードの書き方」
- 名前を付けるときは Skill の `naming-review` を読む

### 決まっている名前の形

| 形 | 使うとき | 例 |
| --- | --- | --- |
| `〜Of(source, …)` | source から引く・導く | `userOf` `pathOf` |
| `is〜` | 真偽を返す | `isDone` `isEmpty` |
| `read〜(stored)` | 保存された、形が保証されない値を読む | `readConfig` `readSaved` |
| `SCREAMING_SNAKE` | モジュールの定数 | `RETRY_LIMIT` `DEFAULT_DIR` |
| `kind` | 判別に使う項目（どの種類の値かを表す）。`type` は TypeScript の `type` と読み違えるので使わない | `{ kind: "expected" }` |

### コメント

書く前に、次の順に判断する。途中で「書かない」に当たったら、判断を終える。

1. 名前と型で言えるか → 言えるなら書かない
2. docs に書いてあるか → 書いてあるなら書かない。場所を示す必要があるときだけ参照を書く
3. 他のファイルに同じ文を書いていないか → 2 箇所に要るなら docs か Skill に 1 本化する
4. 残ったものだけ、次の 3 つの形で書く

| 形 | 中身 |
| --- | --- |
| `/** */` | 呼ぶ側が知る必要のある振る舞い（短絡する / throw する / 副作用がある）。引数の説明も `/** */` に書く |
| `why:` | 言語・OS・ライブラリの挙動から来る理由。意図的に書かなかった処理の理由も含む |
| `TODO:` | 暫定の配置。動かす先と時期を書く |

`@returns` は書かない。`why:` は「何が起きるか → どうしたいか」の形で書き、調査した時点の数値を書かない。

### テスト

振る舞いには書く。見た目には書かない。対象は、イベントの結線・状態の反映・データの変換
——壊れても動かしただけでは気づけないもの。

書いたら壊して確かめる。手順は Skill の `mutation-check`。

## 進め方

**1 ステップ = 1 レビュー。各ステップの終わりで止まる。** 原則 1 ステップ 1〜3 ファイル。
次のステップに勝手に進まない。前のステップで固めたものを変える必要が出たら、黙って直さずに報告する。
詳しくは Skill の `step-plan`。

**出したものは、聞く前に自分で確かめる。** 利用者に聞くのは「どちらが好みか」だけに絞る。
docs を書いたら `spec-writing` の「書いた後の点検」を当てる。
docs の枠線の図は、利用者が PlemolJP で読む前提で幅をそろえる。
`check_spec.py` には `--font ~/Library/Fonts/PlemolJP-Regular.ttf` を渡す。

## 結論する前に確認する

- `which` が空でも「未インストール」と結論しない。絶対パスで確認する
- リポジトリを見れば分かることを質問しない
- 頼まれていない用語訂正や注意書きを、成果物のドキュメントに混ぜない
- エラーメッセージを推測しない。実際に動かして出力を読む

## 環境を壊さない

- 利用者が起動したプロセスを止めない。検証用のサーバは別ポートで起動し、
  終わったら自分が起動したものだけを PID 指定で止める。ポート名やプロセス名で一括 kill しない
- 生成物（`dist/` など）を作ったら片付ける

## git

- `main` への直 push は禁止。作業ブランチを切り、ブランチ名に何をするかを含める
- コミットと push は、指示があるまで実行しない
