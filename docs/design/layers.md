# 設計: 層の分け方

`design-policy.md` の原則を前提にする。原則の理由は `design-policy.md` に書いてあり、設計の docs には書き写さない。

## 設計の docs

| ファイル | 内容 |
| --- | --- |
| `layers.md` | 層の分け方。どの層が何を持ち、どの層を呼んでよいか |
| `directories.md` | ディレクトリの構成 |
| `main.md` | main のモジュールの責務。使う Engine API の一覧 |
| `ipc.md` | main と renderer の間の約束。要求と応答、ストリーム、失敗の値 |
| `renderer.md` | 画面ごとの Model・View・Controller |
| `windows.md` | Windows でしか確かめられない部分 |

## 3 つのプロセス

Electron のアプリは、役割の違う 3 つの部分で動く。

| 部分 | 動く場所 | 持つもの | 持たないもの |
| --- | --- | --- | --- |
| **main** | Node | エンジンへの接続、子プロセス、ファイル、ログ、設定 | 画面 |
| **preload** | renderer の中の、Node と画面の境目 | main を呼ぶ口（`window.api`）を renderer に渡す処理 | 判断。受け取ったものを main に渡すだけ |
| **renderer** | Chromium（画面を描くブラウザ） | 画面 | Node の機能。エンジンへの接続 |

**エンジンに繋ぐのは main だけ**（`design-policy.md` の原則 1）。renderer がエンジンの情報を必要とするときは、
preload が渡した `window.api` を通して main に頼む。

**preload に判断を置かない。** preload は、renderer に渡す関数を並べるだけにする。
判断を置くと、main と preload の 2 箇所を読まないと動きが分からなくなる。

## 層の図

**層**とは、同じ役割のモジュールの集まり。**上の層は下の層を呼ぶ。下の層は上の層を呼ばない。**

```
            ┌────────────────────────────────┐
renderer    │ View（画面の部品）                                             │
            │ Controller（操作を受けて main を呼ぶ）                         │
            │ Model（画面のデータと状態）                                    │
            │ main の窓口（Storybook で差し替える）                          │
            └────────────────────────────────┘
              ↓ window.api を呼ぶ
            ┌────────────────────────────────┐
preload     │ window.api（IPC の口を renderer に渡すだけ）                   │
            └────────────────────────────────┘
              ↓ IPC
            ┌────────────────────────────────┐
main        │ IPC 層        失敗を値に直す、ストリームの登録簿、背圧         │
            ├────────────────────────────────┤
            │ 機能層        接続の状態、コンテナ、イメージ、Compose、設定    │
            ├────────────────────────────────┤
            │ 変換層        Engine API の応答を、画面の型に直す              │
            ├────────────────────────────────┤
            │ Engine API 層 HTTP の要求を組み立て、応答を読む                │
            ├────────────────────────────────┤
            │ OS の窓口     ソケット、子プロセス、ファイル                   │
            └────────────────────────────────┘
              ↓
              エンジン（colima、Docker Desktop、WSL の Docker）
```

## main の中の層

| 層 | 持つもの | 持たないもの |
| --- | --- | --- |
| **IPC 層** | renderer からの要求の受け付け。失敗を値に直す処理（原則 9）。ストリームの登録簿（原則 8）。背圧（原則 7） | 機能の判断。Engine API の呼び方 |
| **機能層** | 仕様（`docs/spec/`）に書いた振る舞い。接続の状態の移り変わり、まとめて削除の順序、Compose の操作 | IPC の扱い。Engine API の URL |
| **変換層** | Engine API の応答を、画面の型に直す純関数（原則 2） | 通信。状態 |
| **Engine API 層** | Engine API の要求の組み立て（版を URL に付ける。原則 6）、応答の読み取り、ストリームの読み取り | 画面の型。機能の判断 |
| **OS の窓口** | ソケットと名前付きパイプへの接続、子プロセスの起動、ファイルの読み書き | Engine API の知識 |

**層を飛ばして呼んでよい。** 機能層は、`docker compose` と `colima start` を実行するときに、
Engine API 層を通らずに OS の窓口を呼ぶ。Compose とエンジンの起動は Engine API に無いため
（`docs/spec/compose.md` の「Compose とは」、`docs/spec/connection.md` の「起動する手段」）。

**ログの記録は、どの層からも呼んでよい。** 層の図には入れていない。
ログは層の役割ではなく、すべての層が同じ形で書くもの（原則 11）。

### 層を分ける理由

| 層 | 分ける理由 |
| --- | --- |
| IPC 層 | **IPC を扱う場所を 1 つにする。** 失敗を値に直す処理とストリームの後始末を、要求ごとに書かずに済む |
| 機能層 | **仕様の振る舞いを 1 箇所に集める。** 仕様を変えたときに直す場所が決まる |
| 変換層 | **Docker の語彙を main の中で止める。** エンジンの版で応答の形が変わっても、直すのは変換層だけで済む（原則 2）。純関数なので、エンジンが無くてもテストを実行できる |
| Engine API 層 | **Engine API の約束を 1 箇所に集める。** 版の付け方とストリームの読み方を、機能ごとに書かずに済む |
| OS の窓口 | **接続方式の違いを、上の層から隠す。** ソケットと子プロセスのどちらで繋いでいても、Engine API 層から見た通信路は同じになる（原則 4） |

## 画面の型は、main と renderer で共有する

**変換層が返す画面の型は、main と renderer の両方から使う。**
型だけを共有し、処理は共有しない。**renderer は main のコードを読み込まない**
——型を置く場所は `directories.md` で決める。

**why: 型を 2 つに分けて書くと、片方だけ直したときに食い違う。**
IPC を越えるときに型の検査は働かないので、食い違いは動かすまで見つからない。

## renderer の中の組み立て

renderer は Model・View・Controller に分ける（原則 14）。

| 部分 | 持つもの |
| --- | --- |
| View | 画面の部品。props を受け取って要素を返す |
| Controller | 利用者の操作を受けて main を呼び、結果を Model に渡す |
| Model | 画面のデータと状態。状態を次の状態へ進める純関数 |
| main の窓口 | `window.api` を呼ぶ処理を 1 つのモジュールに集めたもの |

**main を呼ぶのは、main の窓口だけ。** Controller は main の窓口を通して main を呼ぶ。
Storybook では main の窓口を差し替える（`design-policy.md` の「Storybook を使う条件」）。

画面ごとの組み立ては `renderer.md` で決める。
