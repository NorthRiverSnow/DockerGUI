# 壊して確かめる

**わざと壊してテストが失敗しなければ、そのテストは何も守っていない。**

書いた直後は「通った」しか分からない。通ったのは、正しいからかもしれないし、
**何も検証していないから**かもしれない。区別する方法はひとつしかない。

---

## 1. 壊し方を選ぶ

**テストが守りたい判断を、1 つだけ反転する。** 全部壊すと何が効いたか分からない。

| テストの主張 | 壊し方 |
| --- | --- |
| 「A のときだけ B する」 | 条件を `true` / `false` に固定する |
| 「範囲を絞って処理する」 | 絞り込みを外して全件にする |
| 「X を保存する」 | 保存の呼び出しを消す |
| 「順番が結果を変える」 | 2 つの処理を入れ替える |
| 「既定値は N」 | 既定値を別の値にする |

**引数を消す・戻り値を変える**のも有効。型が通る範囲で最小の改変にする。

---

## 2. 元に戻せるようにしてから壊す

**`git checkout` で戻さない。** 未コミットの変更が消える。実際に失う事故が起きる。

```
cp path/to/target.ts /tmp/target.bak     # 作業用の場所へ退避
# …壊す…
cp /tmp/target.bak path/to/target.ts     # 戻す
```

複数ファイルを壊すなら、まとめて退避する。**壊す前に退避が済んでいることを確認する。**

---

## 3. 壊して、失敗を見る

**そのテストだけを走らせる。** 全件だと、関係ない失敗と区別が付かない。

```
<テストコマンド> <そのファイル>
```

見るのは**失敗した件数**と、**失敗したテストの名前**。

| 結果 | 意味 |
| --- | --- |
| 狙ったテストが失敗した | **合格。** そのテストはその判断を守っている |
| 1 件も失敗しない | **テストが何も守っていない。** 書き直す |
| 関係ないテストまで失敗した | 壊し方が大きすぎる。もっと小さく壊す |

---

## 4. 生き残ったら、テストを疑う前に仕様を疑う

**変異が生き残ったとき、原因は 3 つある。** 順に確かめる。

1. **テストが浅い** — 「呼ばれたこと」だけ見て、結果を見ていない
2. **前提が足りない** — 検証したい状況になっていない
   （例: 「消す」を検証したいのに、消すものが無い状態から始めている）
3. **そのコードが要らない** — 両方の分岐が同じ結果になる。**死んだコードを見つけた**

**3 は収穫。** 消せる。

---

## 5. 戻して、全件のテストを実行する

```
cp /tmp/target.bak path/to/target.ts
<全件のテストコマンド>
```

**戻し忘れたまま進むと、壊れた実装をコミットする。** 必ず最後に全件のテストを実行する。

---

## やりがちな失敗

**コメントだけ変えて「壊した」と思う。** 振る舞いを変えていないので、何も確かめていない。

**複数の判断を同時に壊す。** どれが効いたか分からない。1 回に 1 つ。

**失敗の件数を数えない。** 「失敗した」だけでは、狙ったテストが失敗したか分からない。

**前提が仕様と逆のまま壊す。** テストの前提が間違っていると、正しい実装でも変異が生き残る。
生き残ったら、まず**そのテストが何から始まっているか**を読み直す。
