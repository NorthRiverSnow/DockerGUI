# 名前を付ける・見直す

**名前と型だけで、何を返すか・何を受け取るかが分かるようにする。**

名前が正しければコメントが要らなくなる。**コメントを書きたくなったら、まず名前を疑う。**

---

## 関数は 動詞 + 目的語

**呼ぶと何が起きるかが、名前だけで分かる形にする。**

```
✗ userData()      名詞だけ。取るのか作るのか消すのか分からない
✗ process()       目的語が無い。何を処理するのか
✗ handle()        同上
○ loadUser()
○ validateInput()
○ resetCache()
```

**動詞が要らない形が 2 つある。** どちらも「何を返すか」が形で分かるため。

| 形                | 例                   | 読み方                       |
| ----------------- | -------------------- | ---------------------------- |
| `〜Of(source, …)` | `userOf(list, id)`   | 「list の user」。返すのは値 |
| `is〜` / `has〜`  | `isDone(state)`      | 真偽を返す                   |

---

## 引き方が複数あるなら、名前に出す

**同じものを別の条件で取るなら、条件を名前に足す。**

```
✗ findUser(id) と findUserByEmail(email)   ← 片方だけ条件が付いていて、対にならない
○ findUserById(id) と findUserByEmail(email)
```

**引数の型だけでは区別が付かないときに要る。**

```
✗ get(key)              どこから取る？
○ getFromCache(key)
○ getFromStore(key)
```

**足しすぎない。** 引き方が 1 つしかないなら `findUser(id)` で十分。
**2 つ目の引き方が出たときに、両方に足す**——片方だけ付けると、どちらが既定か読めなくなる。

---

## 付ける前に、上から確かめる

### 1. 返すものを名乗っているか

呼ぶ先の都合で名付けない。**その関数が何を返すか**で名付ける。

```
✗ dataForTable   （テーブルに渡すため、は呼ぶ側の都合）
○ visibleRows    （返すのは表示する行）
```

### 2. 目的語がずれていないか

```
✗ dropUsers      （利用者そのものを消す？）
○ resetUserStats （消すのは利用者の記録）
```

**「消す」「戻す」「外す」「出す」は目的語が無いと複数の意味に取れる。**

### 3. 同種の関数と動詞が揃っているか

```
✗ dropCache  と resetIndex
○ resetCache と resetIndex
```

**対になる関数は、対になる動詞で。** `load` / `save`、`open` / `close`。
片方だけ `fetch` と `save` のように混ぜない。

### 4. 対になる関数と区別が付くか

単位や範囲が違うなら、名前に出す。

```
✗ count（件数？回数？） と total
○ itemCount と attemptCount
```

### 5. 仕様書の言葉を使っているか

比喩と内部語を避ける。**仕様に出てくる言葉があるなら、それを使う。**

```
✗ pool             （何の入れ物か分からない）
○ targetItems      （仕様の「処理の対象」）
```

### 6. 引数の名前が、何が入るかを言っているか

```
✗ parsed   （何をパースした？）
○ stored   （保存から読んだ、形が保証されない値）
```

### 7. 引数の順が同族と揃っているか

```
✗ f(items, source) と g(source, item)
○ どちらも (source, …)
```

### 8. 判断に名前が付いているか

条件式を裸で置かない。**名前を付けると、その判断が仕様のどれかが分かる。**

```
✗ if (all.every((x) => selected.includes(x)))
○ if (isEverySelected(all, selected))
```

---

## 短縮しない

`of` `res` `val` `tmp` `data` `info` のような名前を使わない。

**テストのヘルパも同じ。** 何を固定したかを名前に入れる。

```
✗ const of = (a, b) => …
○ const emptyProgress = (counts, answers) => …
```

---

## 置き場所も名前の一部

**共通部分は、使う側の都合ではなく中身で分ける。**

「両方から使うから共通」ではなく、「**何の集まりか**」でファイルを分ける。
名前もそれに従う（`〜.common.ts` より `keys.ts` のように中身を言う名前がよい）。

**同じ処理が 2 箇所に出たら、3 箇所目を書く前に共通へ移す。**

---

## テスト名も同じ規則で付ける

**テスト名は「何を検証したか」を言う。** 状況設定は名前に詰め込まず、本体か `why:` に書く。

```
✗ it("外した項目は、開き直しても外れている")
○ it("一覧の項目のチェックを外すと、画面を開き直してもその項目のチェックは外れたまま")

✗ it("途中の記録が保存に残っていても、選ばなければ出ない")
○ it("選ばなかった項目は対象に入らない")   ← 状況は why: へ
```

---

## 直した後に確かめる

**名前を変えたら、呼ぶ側を全部読み直す。** 機械的な置換だけだと、
新しい名前が文脈に合わない箇所が残る。

**コメントも見直す。** 名前が正しくなったぶん、要らなくなったコメントがある。
