# 日本語を書く

**書いた本人以外が読んで、同じ意味に取れる文にする。**

日本語は主語と目的語を省略でき、多義語が多い。放っておくと、書いた本人にしか読めない文が残る。

プロジェクトで決まっている言葉（「A ではなく B を使う」）は、プロジェクトの CLAUDE.md に書く。
writing-ja には、どのプロジェクトでも使える規則だけを書く。

---

## 1. 主語が変わるときは主語を書く。目的語は省略しない

**主語が前の文と変わるときは、主語を書く。** 省略すると、読む人は前の文の主語が続いていると読む。

```
✗ リセットは押した項目だけを未着手に戻す
○ リセットのボタンは、押した項目だけを未着手に戻す

✗ 行を選ぶと入力欄に変わる。確定すると一覧を更新する
    （何が入力欄に変わるのか。一覧を更新するのは誰か）
○ 行を選ぶと、行の名前が入力欄に変わる。利用者が確定すると、DockerGUI は一覧を更新する
```

**主語が変わらない文では、主語を繰り返さない。** 同じ主語が続くと文が硬くなり、読む人が要点を拾いにくくなる。

```
✗ DockerGUI は入力欄を閉じる。DockerGUI は元の名前を表示する。DockerGUI は一覧を更新する
○ DockerGUI は入力欄を閉じて元の名前を表示し、一覧を更新する
```

**目的語は、主語が同じでも省略しない。** 動詞ごとに、目的語が何かを確かめる。

```
✗ 外した項目は、開き直しても外れている
○ 一覧の項目のチェックを外すと、画面を開き直してもその項目のチェックは外れたまま

✗ 自動で回る
○ テストで検証する
```

**特に危ないのは「外す」「消す」「戻す」「出る」「変わる」。** 目的語が無いと複数の意味になる。

---

## 2. 多義語を使わない

```
✗ lint で落とす         ○ lint エラーにする
✗ テストが落ちる         ○ テストが失敗する
✗ 空行を落とす           ○ 空行を削除する
✗ コントラストが落ちる    ○ コントラストが下がる
✗ HMR で拾われない       ○ HMR の対象外
✗ テストを流す           ○ テストを実行する
✗ ルールが効く           ○ ルールが適用される
✗ 例外を上げる           ○ 例外を throw する
✗ サーバを上げる         ○ サーバを起動する
✗ 検証を通す             ○ 検証が正常終了する
✗ 印                     ○ アイコン（画面に出す絵。「印」は記号にも強調にも読める）
```

**「落とす」は特に禁止。** lint エラーか、要素の削除か、値の低下か、区別が付かない。

---

## 3. 因果を書く。状況だけで終わらせない

**「何が起きるか → だからどうするか」の形にする。**

```
✗ 実データに 3 本ある
○ 連続する改行をまとめると行が 1 つ減り、間を空けて区切っていた文が地続きに見える
```

**調査した時点の数値は書かない。** 「153 行中 4 本」「最長 41 字」は元データが変われば嘘になる。
残すのは、いつでも成り立つ因果のほう。

---

## 4. 当然の疑問に先回りする

読む人が最初に思う疑問に答えていない説明は、読む人の判断に使えない。

```
✗ 空の要素にも min-height を与える
○ 中身が空だと高さが 0 になり、隣の列と行がずれる。min-height で 1 行ぶんを確保する
```

---

## 5. 経緯を書かない

**「以前は X だったが Y にした」は git log の役目。** ドキュメントは現行の姿だけを書く。

```
✗ 当初は接続画面を出していたが、api が無い環境では意味が無いので消した
○ api が居なければ接続画面を出さない
```

---

## 6. 難しい漢字と古い表記を使わない

**読めない字が 1 つあると、読む人は先へ読み進められなくなる。** 画面に出る言葉は、
利用者が普段目にする形にする。

```
✗ 釦      ○ ボタン
✗ 複写    ○ コピー
✗ 鍵      ○ キー（キーボードのキー。「鍵」は錠前に読める）
✗ 頁      ○ ページ
```

**外来語はカタカナで書く。無理に漢字へ直さない。**

**英単語を日本語の文に混ぜない。**

```
✗ 最初に focus が当たるのは「やめる」
○ 最初にフォーカスが当たるのは「やめる」
```

---

## 7. 指示語と代名詞を使わない

**「これ」「それ」「ここ」「この〜」で指した先を、読む人は前に戻って探すことになる。**
名前で呼ぶ。

```
✗ DockerGUI はここを直接叩く
○ DockerGUI は Engine API を直接呼び出す

✗ その行が消えた場合だけ、選択を外す
○ 選んでいる行が消えた場合だけ、選択を外す

✗ この場合だけは選ばせる
○ 候補が複数のときだけは選ばせる
```

### 作っているものは名前で呼ぶ

```
✗ この道具は同時に 1 つのエンジンにしか繋がない
○ DockerGUI は同時に 1 つのエンジンにしか繋がない
```

「道具」では何を指すか読めない。Storybook のような外部のものを指すときは「手段」と書き分ける。

### 表や節も、位置ではなく名前で呼ぶ

```
✗ 上の表に当てはまらない環境では、起動を試みない
○ 「起動する手段」の表に当てはまらない環境では、起動を試みない
```

**why: 位置で指すと、あとから文章を足したときにずれて嘘になる。**
名前で指せば、節が動いても正しいままになる。

### 残してよいのは、指す先を持たない慣用句だけ

```
○ そのままコピーできる形    （「そのまま」は前の語を指していない）
○ それぞれのディストロ
○ それでも Tauri を選ばない
○ その場で入力欄に変わる
```

---

## 8. 言葉を定義してから使う

### 独自の呼び方は、使う前に定義する

画面の部分を指す言葉は、最初に出てくる場所で名前を決め、以降は決めた名前だけを使う。

```
✗ 画面の上部に帯を出す
○ 上部の領域を**状態バー**と呼ぶ  … と定義してから、以降は「状態バー」を使う
```

### 説明を用語の表に詰め込まない

表の 1 行は 1 つの意味に留め、説明が要るなら節を分ける。

```
✗ | Docker Engine | コンテナを動かすサーバ。このアプリはエンジンに「起動して」と頼む側で、
                    コンテナを動かすのはエンジン |
○ | Docker Engine | コンテナを動かしているサーバ（「Docker の構成」を参照） |
```

詰め込むと、定義と説明が混ざって両方読めなくなる。
✗ の例は「起動して」の目的語が無く、コンテナの起動かエンジンの起動かも読めない。

---

## 書いた後の点検

**1 文ずつ、次の順に当てはめる。**

1. 主語が前の文と変わっているのに、主語を省略していないか
2. 目的語は書いてあるか。**「何を」**
3. 多義語を使っていないか
4. 状況で終わっていないか。**因果になっているか**
5. 経緯が混ざっていないか
6. 読めない字を使っていないか。**外来語を漢字に直していないか**
7. 指示語で済ませていないか。**名前で呼べないか**
8. 独自の呼び方を、定義せずに使っていないか
9. プロジェクトの CLAUDE.md で決まっている言葉を使っているか

**とくに見落としやすいのは、自分が書いた規則の文そのもの。**
「主語を書く」と書いた文で主語を省略していることがある。
